# ZXV Streaming TRD — потоковое видео для ZX Spectrum 128

Это второй прототип ZXV: видеопоток больше не загружается целиком в память.
TRD содержит BASIC-загрузчик, резидентный Z80-плеер и отдельный файл `VIDEO.C`,
который читается секторами во время воспроизведения.

## Однофазный вариант с предварительной загрузкой

Для короткого 24-кадрового ролика есть отдельный профиль без фонового чтения
диска и без временного чередования A/B:

```bash
python build_preloaded_single_phase_trd.py \
  --output build_preloaded_single
```

Его `VIDEO.C` занимает 31 744 байта (124 сектора). При запуске файл целиком
загружается в банки 0 и 1, после чего TR-DOS больше не вызывается. Банк 5 и банк
7 служат обычными двойными экранными буферами: полный следующий кадр сначала
копируется и декодируется в скрытый экран, а затем один раз становится видимым.
Если подготовка занимает больше времени, предыдущий экран остаётся видимым
целиком; частично обновлённый кадр не показывается.

Полный цикл и отсутствие чтений после preload можно проверить в Fuse:

```bash
python smoke_test_fuse.py /path/to/fuse \
  build_preloaded_single/zxv_preloaded_single_phase.trd \
  --metadata build_preloaded_single/build_metadata.json \
  --hits 25 --forbid-read-after-preload
```

## Длинное видео с дизерингом средствами плеера

`build_long_video_trd.py` хранит кадр как 128×96 логических пикселей по два
бита яркости — четыре уровня. Z80-плеер таблично разворачивает каждый уровень в
одноточечный паттерн 2×2 на реальном экране 256×192. Поэтому точки дизеринга
имеют нативный размер, хотя пространственная детализация исходного состояния
остаётся 128×96.

Атрибуты не уменьшаются: поток содержит штатную сетку 32×24, один байт для
каждого реального знакоместа 8×8. Полное состояние кадра занимает 3840 байт:
3072 байта яркостей и 768 байт атрибутов.

Для каждого знакоместа кодировщик перебирает все 112 допустимых ориентированных
пар INK/PAPER в обычной и яркой палитрах Spectrum. Поэтому соседние оттенки
могут передаваться не только сочетаниями цвета с белым или чёрным, но и, например,
синим с голубым, зелёным с жёлтым или красным с пурпурным. Перебор выполняется
офлайн и не меняет формат атрибутов либо скорость плеера.

Перед цветовым кодированием применяется один неподвижный центральный crop с
масштабом 1,25×. По 10% исходной ширины отрезается слева и справа; положение и
масштаб не меняются на протяжении ролика. Это исключает ложное движение всего
кадра и улучшает межкадровое сжатие.

Перед кодированием выполняется отдельный проход по всему выбранному фрагменту.
Для каждого кадра строится гистограмма линейной яркости активной области.
Пороги вычисляются по центрированному окну длительностью 4 секунды: нижние 3%
и верхние 3% отсекаются, а внутренний диапазон делится алгоритмом Lloyd–Max на
четыре группы. Затем параметры сглаживаются симметричным треугольным фильтром
длительностью 1 секунду. Поэтому диапазон плавно следует за сценой без резких
скачков и «дыхания» яркости. Эта обработка выполняется при кодировании и не
требует дополнительных вычислений от плеера. Чёрные поля 128×96 в анализ не
входят.

Звуковая дорожка сводится из исходного 5.1 в mono и анализируется спектрально.
Три сильнейшие устойчивые тональные линии привязываются к ближайшим нотам и
записываются как делители и громкости каналов A/B/C музыкального сопроцессора
AY-3-8912/YM2149F. Общая громкость дополнительно следует за RMS исходной
дорожки: тихие и громкие эпизоды отображаются на диапазон AY 0–15, а внутри
него сохраняется относительная громкость трёх нот. Состояние занимает 9 байт
на кадр и обновляется вместе с готовым экраном с частотой 25/3 Гц, поэтому звук
практически не отнимает время у декодирования. Генератор шума AY отключён.

По умолчанию исходник выбирается с частотой 25/3 fps. Экранный планировщик
удерживает каждый готовый банк 5/7 ровно шесть полей 50 Гц, получая точные
25/3 fps без неравномерного чередования:

```bash
python build_long_video_trd.py \
  --input-video big_buck_bunny_1080p_h264.mov \
  --duration 120 \
  --fps 25/3 \
  --timing-fps 25/3 \
  --dither ordered4 \
  --fixed-center-zoom 1.25 \
  --output build_long_center_crop_colour_ay_25over3fps
```

XOR-дельты сжимаются командами пропуска нулей, повторения байта и литералов.
Если двухминутный поток не помещается в 640-КиБ TRD, генератор автоматически
создаёт несколько независимо загружаемых частей. Каждая часть начинается с
полного ключевого кадра.

## Fast-sparse профиль

`build_fast_sparse_trd.py` переупаковывает готовый компактный поток в формат,
который обновляет скрытый экран непосредственно во время чтения каждого
сектора. Для каждой изменённой строки выбирается либо 32-битная маска, либо
короткий список точек; индексы изменённых атрибутов кодируются промежутками.
Банки 5 и 7 сами служат опорными кадрами, поэтому полный рендер 128×96 →
256×192 из основного цикла удалён.

```bash
python build_fast_sparse_trd.py \
  --source-build build_long_motion_crop_colour_ay_25over3fps \
  --output build_fast_sparse_25over3fps
```

Профиль сознательно увеличивает средний пакет ради скорости Z80. Команды
применяются сразу после чтения сектора и обычно успевают выполниться до
следующего поля 50 Гц. Если пакет занимает больше шести секторов, предыдущий
кадр удерживается дольше.

Для пакетов больше пяти секторов упаковщик дополнительно пробует простой RLE
плотных 32-байтных строк яркости. Серии из трёх и более одинаковых байтов
кодируются парой «длина, значение», остальные байты — короткими литералами.
RLE используется только если реально уменьшает число дисковых секторов;
разреженные строки продолжают декодироваться прежними быстрыми командами.

Основной кодировщик использует обратную связь rate–distortion. Для каждого
кадра он пробует несколько штрафов за смену атрибута, реконструирует реальное
изображение Spectrum, измеряет ошибку в линейном RGB и оценивает будущий
fast-sparse пакет относительно того же экранного банка. Среди вариантов не
более шести секторов выбирается вариант с минимальным искажением, но не хуже
заданного предела относительно базового режима. Если подходящего варианта нет,
сохраняется базовый кадр, поэтому экономия места не достигается ценой заметной
потери качества.

Каталог TR-DOS:

- `boot.B` — BASIC-автозагрузка;
- `PLAYER.C` — резидентный плеер по адресу `6000h`;
- `VIDEO.C` — 240 секторов потокового видео.

## Видеорежим

- ZX Spectrum 128;
- экран A — обычный экран в банке 5;
- экран B — теневой экран в банке 7;
- аппаратное чередование A/B — 50 Гц;
- одинаковые атрибуты в A и B;
- три временных уровня пикселя: PAPER/PAPER, INK/PAPER, INK/INK;
- Floyd–Steinberg применяется кодировщиком, а не Spectrum.

Для сборки без заметного временного мерцания используется `--no-flicker`.
В этом режиме банк 5 постоянно остаётся видимым, а его пространственно
дизерированная фаза A обновляется с частотой логических кадров. Банк 7 и фаза B
сохраняются в потоке для совместимости формата, но на экран не переключаются.

Демо содержит 24 автоматически перекодированных исходных кадра с движущимися
кругом, прямоугольником и ромбом, серой шкалой и статической сеткой. Полный
циклический проход занимает около 4,8 секунды, не считая короткой начальной
задержки.

## Потоковая архитектура

В фиксированной памяти расположены два буфера:

```text
8000h–9FFFh  пакет, который сейчас декодируется
A000h–BFFFh  пакет, который подкачивается с диска
```

После каждого переключения экрана плеер может прочитать один следующий сектор
в неактивный буфер. Когда текущая пара A/B была показана нужное количество раз,
буферы меняются ролями.

Если диск не успел загрузить пакет, текущий кадр показывается дольше. Неполный
пакет никогда не передаётся декодеру.

## Структура VIDEO.C

```text
1 сектор   заголовок ZXV Streaming
27 секторов  исходный экран A, 6912 байт
27 секторов  исходный экран B, 6912 байт
N секторов   циклические пакеты переходов
```

Каждый пакет начинается с числа занимаемых секторов, времени удержания пары A/B
и длин двух дельт. После последнего пакета дисковый указатель возвращается к
первому; последний пакет уже переводит последний кадр обратно в исходный.

## Сборка

```bash
python build_streaming_trd.py --frames 24 --output build
```

Без 50-Гц чередования экранов:

```bash
python build_streaming_trd.py --frames 24 --no-flicker --output build
```

Из произвольного видео:

```bash
python build_streaming_trd.py \
  --input-video input.mp4 \
  --frames 24 \
  --output build
```

Количество кадров пока ограничено максимальным размером одного файла TR-DOS —
255 секторов. Следующая версия может разбивать поток на `VIDEO00`, `VIDEO01` и
читать их как один физически непрерывный секторный поток.

## Проверка

```bash
python validate_streaming_player.py \
  build/zxv_streaming_128.trd \
  --metadata build/build_metadata.json
```

Валидатор выполняет реальный машинный код плеера в небольшом интерпретаторе Z80,
моделирует банки 5/7 и вызовы TR-DOS, а данные читает из готового TRD.

Для приложенного образа проверено:

- 248 экранных полей;
- 24 потоковых пакета;
- 190 вызовов секторного чтения;
- 62 976 прочитанных байт;
- оба экранных банка после полного цикла побайтно вернулись к исходной паре;
- стек не опускался ниже `5FEAh`.

Дополнительный smoke-тест запускает образ в Fuse и завершается только после
реального чтения начальных экранов и достижения `main_loop`:

```bash
python smoke_test_fuse.py /path/to/fuse build/zxv_streaming_128.trd \
  --metadata build/build_metadata.json --hits 25
```

Значение `--hits 25` требует пройти начальный вход и все 24 потоковых пакета
перед успешным завершением теста.

## Ограничения

Полноценного Spectrum-эмулятора в среде сборки не было. Образ проверен:

1. независимым Python-декодером формата;
2. инструкционным валидатором машинного кода;
3. анализом каталога и секторного размещения TRD.

Плеер рассчитан прежде всего на Fuse/Unreal/Retro Virtual Machine, Gotek,
DivMMC/SD и другие быстрые реализации Beta Disk. Стандартная функция чтения
TR-DOS блокирующая; на механической дискете вращательная задержка может растянуть
отдельные поля и создать заметное мерцание.

Плеер постоянно сохраняет бит 4 порта `7FFDh` установленным. Это оставляет
выбранным 48K ROM, чтобы Beta Disk могла автоматически подключить ROM TR-DOS при
выборке инструкции по адресу `3D13h`. Выбор 128K ROM значением `07h` приводит к
переходу в системный ROM вместо диспетчера TR-DOS и останавливает запуск до
первого кадра.
