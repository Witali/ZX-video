# Компенсация движения с ограниченными изменениями точек

Дата: 18 сентября 2026. База `66257b4`; точный контроль с группами по 8
сохранён в `a5a49f9`, его метка базы уточнена в `cd1ae5a`.
**Офлайн-опыт. Новых проигрываемых TRD и подтверждения скорости Z80 нет.**

## Метод и ограничения

Полный фильм — 4971 кадр, 128×96 логических / 256×192 физических пикселя,
25/3 кадра/с. Все атрибуты сохраняются побайтно, AY 50 Гц не изменяется.
Формат `FMR1` и независимый декодер взяты из
[точного опыта движения](FINE_MOTION_RESULTS_ru.md): блоки 8×8 логических
пикселей, 81 смещение в пределах ±4 и нулевой предиктор, история n−1.

Поиск на ПК может убрать **отдельный байт поправки**, даже если остальные
байты ячейки нужно исправить. Ограничения относятся к исходному кадру:

- Не более 2 изменённых логических пикселей в физической ячейке 8×8.
- Разница заполнения каждого — не более четверти. При существующих
  вложенных узорах это изменяет один физический пиксель на логическое изменение.
- RMSE RGB, усреднённого по 2×2, не более 24 для ячейки.
- После одного неточного кадра ячейка принудительно восстанавливается
  точно. Счётчик относится к фиксированной ячейке экрана, а не движущемуся объекту.
- Дополнительно не более 64/128/256 логических изменений на весь кадр.
  Изменения при одинаковых INK/PAPER тоже расходуют бюджет, хотя не видны.

ПК жадно выбирает выгодные отмены поправок по отношению стоимости байта
к числу изменяемых пикселей. Затем выбирает вектор, при равной стоимости
предпочитая меньшую ошибку, и применяет общий бюджет кадра. Последний шаг
может вернуть часть точных поправок; поиск не является глобально оптимальным
по окончательному размеру ZX0. Ошибка относительно отфильтрованного кадра
никогда не заменяет проверку относительно текущего исходного.

Проверены группы 8/16 кадров: **3 последовательности, 6 полных потоков**.

## Отбор по размеру

DEFLATE, блоки 8192 байта; это только отбор перед настоящим ZX0:

| Лимит точек на кадр | Группы 8 | Группы 16 |
|---|---:|---:|
| Точный контроль | 2574394 | 2542062 |
| 64 | 2485499 | 2456301 |
| 128 | 2439178 | 2409986 |
| 256 | 2428843 | 2398938 |

Для дальнейшего опыта выбран **128 / группа 8**: буфер векторов/масок
5376 байт. Повышение лимита до 256 экономит лишь 10335 байт (0,42%)
в отборочном замере, удваивая максимальную долю изменённых пикселей.
Его не продвигаем как основной вариант. Это решение по совокупности
предварительного размера и измеренного качества; отдельного ZX0-замера
варианта 256 в этой серии нет.

### Оптимальный ZX0

Блоки 8192, включая 4-байтовые заголовки, полное видео:

| Изображение, группа 8 | Байт ZX0 |
|---|---:|
| Точный контроль | 2679898 |
| Лимит 128 | **2537085** |

Экономия **142813 байт (5,33%)**. Все 615 блоков кандидата независимо
распакованы. Это на 123868 байт меньше прежнего точного варианта с группой
16, но в таком сравнении меняются и изображение, и буферизация.

С прежним замером AY 77696 байт получается 2614781 байт, превышение
бюджета трёх TRD 1937664 на **677117 байт до служебных расходов**.
Нужно убрать ещё около 25,90% этой суммы. Поэтому вариант в выпуск
не включается; качество и скорость нового проигрывателя ещё не приняты.

## Качество всех кадров

Эталон — принятое **Spectrum-изображение**, не исходный HD-мультфильм.
Область сравнения 256×144, без чёрных полос. SSIM не является процентом качества.

| Лимит | Изменённые RGB-пиксели, среднее / максимум | SSIM средний / минимум |
|---|---:|---:|
| 64 | 0,141974% / 0,173611% | 0,994463 / 0,980174 |
| 128 | 0,204015% / 0,347222% | 0,991185 / 0,966887 |
| 256 | 0,222975% / 0,694444% | 0,990427 / 0,952953 |

Для 128: PSNR усреднённого по 2×2 RGB 33,216 дБ, худшего кадра 30,615 дБ;
1-й процентиль SSIM 0,975612. Восстановленные пиксели и ячейки независимо
проверены настоящим рендером: максимум последовательных кадров с ошибкой
**1** для всех трёх вариантов. Новых целиком повторённых кадров нет.

Дополнительно измерены изменения между соседними кадрами. «Пропущено» —
исходный RGB в позиции меняется, а кандидат остаётся прежним; «добавлено» —
исходный RGB постоянен, а кандидат меняется. Это счётчики пиксельных событий,
не оценка оптического потока и не проверка направления/величины всех изменений.

| Лимит | Пропущено точек на переход, среднее | Добавлено, среднее | Доля пропущенных исходных событий |
|---|---:|---:|---:|
| 64 | 50,898 | 51,867 | 1,8942% |
| 128 | 71,879 | 75,506 | 2,6750% |
| 256 | 78,030 | 82,889 | 2,9039% |

Таким образом, высокий SSIM не означает отсутствия временных искажений.
Ограничение по ячейкам не доказывает сохранность каждой движущейся детали.
Просмотрены последовательности по пять кадров для худших событий лимитов
64 и 128. Для 128 это 4360–4364, 2112–2116, 1006–1010; различия выглядят
как редкие точки, крупные формы и цвета сохранены. Это контактные полосы,
**не полный просмотр фильма на скорости воспроизведения**.

## Проверки, память и решение

- 6 потоков независимо декодированы в ожидаемые кадры FMR1.
- Для каждого кадра проверены пределы ячейки, общий бюджет и счётчик ошибки.
- SSIM и переходы измерены для всех 4971 кадров каждого из 3 вариантов.
- 5 тестов пройдены: отдельные байты одной ячейки, ошибка/срок,
  общий бюджет/принудительное исправление, точный контроль поиска движения,
  раздельный подсчёт пропущенных и добавленных изменений.
- SHA-256 выбранных кадров:
  `cab64f41c1046d8b9a59c4adbe009029ee6b37d52d22ccd9877644fd376dffa2`.
- Буфер векторов/масок 5376 байт; две компактные истории ещё 7680.
  Это не полная память проигрывателя: экраны, ZX0, код/стеки, AY/IRQ и TR-DOS
  остаются обязательными. Уменьшенное дисковое кольцо не проверялось.
- PLAYER/TRD не менялись, **разница горячего пути 0 T**. Новых Z80 T-states,
  ROM/ULA/IRQ, дисковых и Fuse-замеров нет; 8⅓ fps нового формата не доказаны.

Дальнейшее усиление удержания пока не выбрано. Следующий кандидат должен
сокращать точный остаток: более подходящий порядок полей и табличное
предсказание промежуточного положения между соседними пикселями. Для выпуска
по-прежнему нужны объём трёх TRD с полным звуком и служебными расходами,
проверка движения и полный Z80/Fuse-прогон.

## Воспроизведение

`CHECKPOINT` — полный принятый `source/conversion.npz`; `ZX0` — ZX0 v2.
Для отчётов качества повторить команду с BUDGET=64,128,256.

```text
python toolkit/probe_bounded_motion.py --checkpoint CHECKPOINT --cache .tmp/bounded_motion --output toolkit/bounded_motion_measurements.json
python toolkit/review_motion_quality.py --reference CHECKPOINT --candidate .tmp/bounded_motion/bounded_motion_p2_bBUDGET_a1_e24.npz --output toolkit/bounded_motion_qualityBUDGET.json --filmstrip .tmp/bounded_motion/filmstripBUDGET.png
python toolkit/probe_zx0_storage.py --raw .tmp/bounded_motion/bounded_motion_p2_b128_a1_e24_g8.raw --block-bytes 8192 --zx0 ZX0 --cache .tmp/bounded_motion_zx0 --output toolkit/bounded_motion_zx0_128_measurements.json
python -m unittest discover -s toolkit -p test_bounded_motion.py -v
```

Данные: [шесть раскладок](bounded_motion_measurements.json),
[качество 64](bounded_motion_quality64.json), [качество 128](bounded_motion_quality128.json),
[качество 256](bounded_motion_quality256.json), [ZX0](bounded_motion_zx0_128_measurements.json).
