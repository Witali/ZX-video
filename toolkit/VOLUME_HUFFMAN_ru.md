# Отдельная настройка Хаффмана для самостоятельных дискет

## Что проверяется

База — `53d7a1e`, FAP3 `1aff3a304635025c…`, 4221 кадр после разрешённого
удаления титров. Разбиение: 1614 / 1306 / 1301 кадров, конечные номера
1614 / 2920 / 4221. Разрешение, все компактные кадры и 25 326 записей AY
не меняются. Измерены размер, изолированный декодер и полное воспроизведение
трёх самостоятельных TRD. **Это не выпуск: сроки кадра и AY не пройдены**.

Сохраняем исходное соответствие 256 предсказанных байтов 16 контекстам
и отдельный контекст атрибутов. Пересчитываем длины кодов по частотам
байтов, действительно попавших в энтропийный поток. Литеральные фрагменты
не участвуют в статистике. Сравниваем одну общую настройку и три настройки
по содержимому отдельных томов.

Для каждого варианта сохраняем символы, встречающиеся во всём фильме,
с минимальной частотой 1. При необходимости удваиваем этот нижний предел,
чтобы максимальная длина не превышала исходные 17 бит. Пустое или
односимвольное дерево дополняем до двух листьев. Проверяем полное дерево,
размещение банка таблиц и размещение кода настоящим сборщиком.

Это ограниченный поиск: контексты не перегруппированы; сначала границы
фиксированы, затем проверено соседнее разбиение. Результат не доказывает
предел сжатия.

| Исходные | 2541 / 2585 / 2561 | 7687 | 55 | 1 929 800 |
| Пересчитанные общие | 2525 / 2571 / 2555 | 7651 | 19 | 1 922 282 |
| Индивидуальные | 2523 / 2570 / 2545 | 7638 | 6 | 1 920 009 |

Максимальная длина кода: 17 → 16 для общей настройки, → 15 для каждой
индивидуальной. Банк таблиц после разностей и ZX0: 4120 → 3448 байт
(общий), либо 3247 / 3207 / 3210 байт. Три диска на этих границах
**не помещаются**: проверять нужно каждый том, а не только общую сумму.

Символы Хаффмана занимают 3 411 034 → 3 350 037 бит с общими таблицами,
либо 3 332 916 бит в сумме трёх индивидуальных диапазонов. Однако число
дорогих кодов длиннее 8 бит **растёт**: 32 040 → 42 306 / 43 329.

Проверено 22 904 случая исполнения опкодов для каждого из пяти комплектов
таблиц, всего 114 520; значения, конечная битовая позиция и такты совпали
с формулой. Скалярная проверка полных кадров/AY выполнена для всех пяти
целых потоков. Новых изменений пикселей нет.

**Вывод:** обычная минимизация битов не минимизирует время этого Z80
декодера. Уменьшение максимальной длины кода само по себе недостаточно:
имеет значение, сколько реальных символов вышло за 8-битную таблицу.
Нужна оценка полного тракта и, возможно, подбор длин с учётом стоимости
длинной ветви. Автоматически включать новый вариант по размеру нельзя.

Полные данные: [размеры](volume_huffman_probe.json),
[изолированные такты](volume_huffman_cpu.json).

## Защита качества и независимого запуска

`probe_volume_huffman.py` сначала восстанавливает последовательность
кодируемых символов из состояний кадров и неизменённых векторов/масок.
Повторное кодирование старыми таблицами должно дать **весь исходный файл
побайтно**. Далее меняются только длины таблиц, энтропийные байты, их длина
и число значащих битов. AY, маски, векторы, карты вывода и литералы
копируются из исходных пакетов.

Каждый новый FAP3 целиком декодируется существующим независимым скалярным
декодером и сравнивается со всеми 4221 состояниями; записи AY сравниваются
с исходными. Перенос данных из RAM предыдущего диска не используется.
Сборки включают собственные таблицы, код, начальные экраны, компактный
предыдущий кадр и состояние AY; `warm_continuation=False`.

Индивидуальные FAP3 имеют разные идентификаторы серии. Поэтому первый
скрипт сохраняет метаданные расчёта, а TRD не публикует. Последующий
`measure_volume_huffman.py` задаёт единый отпечаток всех трёх источников,
состояний кадров, границ и параметров сборки. Меняются только 16 байт ID
в секторе 15 и 16 байт ожидаемого следующего ID внутри PLAYER. Все остальные
байты образа проверяются на неизменность; исполняемые инструкции прежние,
разница тактов этой замены — 0 T. Два перехода проверены реальными
опкодами с подменённой ROM: чужая серия/неверный номер отвергаются,
правильный диск принят, RAM совпадает с отдельным холодным запуском.

## Что входит в размеры

Используется настоящий `Builder.volume`, оптимальный ZX0, полные
загрузочные секции и раскладка последних дорожек. Опции: `fast_disk`,
`cached_seek`, `interleaved`, `cold_bitmaps`, `startup_delta`; без deferred
и inline-matches. На каждый TRD доступно 2544 сектора по 256 байт.
Кешированные блоки проверяются обратной распаковкой. Сохранённые отчёты
содержат размеры всех загрузочных секций и точные SHA входов/результатов.

## Как считаются такты

`profile_volume_huffman.py` использует формулы существующего
`benchmark_prefix_huffman.py`, проверенные по инструкциям
[`prefix_huffman_z80.py`](prefix_huffman_z80.py) и таблице
[Zilog Z80 CPU User Manual](https://www.zilog.com/docs/z80/um0080.pdf).
Дополнительно исполняются реальные опкоды для каждой встречающейся пары
контекст/символ при всех восьми начальных битовых позициях.

Для короткого кода (длина `L≤8`, начальная позиция `s`, `a=1` для атрибутов):

`168 + 5·[s+L≥8] − a` T.

Для длинного кода:

`420 + 53·(L−9) + 32·refills − carry + 70·[s>0] + 5·[end>0] − a` T,

где `end=(s+L) mod 8`, `available=8−s` при `s>0`, иначе 0,
`refills=ceil(max(0,L−8−available)/8)`, а `carry` — перенос при адресации
символа в хвостовой таблице. Позиция обнуляется в начале каждого пакета.

Суммируются реальные длины и позиции всех символов выбранного тома;
абсолютные значения до/после и разница сохранены в отчёте. Алгоритм Z80
не изменён, но меняются таблицы, константы и развёртка максимальной длины.
Стоимость зависит от данных, поэтому нельзя приписывать всему декодированию
нулевую разницу тактов только на основании неизменённого исходника.

**Исключены из формул** обёртки, движение, ZX0, запись экранов, IRQ/ULA,
TR-DOS ROM, доставка секторов и старт. Эти числа нельзя называть скоростью
всего проигрывателя. Полные Fuse-измерения приведены отдельно ниже.

## Три самостоятельных диска: полная проверка

`rebalance_volume_huffman.py` проверил 27 реальных раскладок:
19 конечных границ первого тома 1612..1630 и четыре пары оставшихся томов.
При границах **1625 / 2921 / 4221** все три образа помещаются:

| Том | Кадры | Занято секторов | Свободно | Видео ZX0, байт |
|---|---:|---:|---:|---:|
| 1 | 1625 | 2544 | 0 | 641 486 |
| 2 | 1296 | 2542 | 2 | 639 731 |
| 3 | 1300 | 2542 | 2 | 638 742 |
| Всего | 4221 | 7628 | 4 | 1 919 959 |

Это настоящие собранные TRD. Каждый прошёл отдельный холодный старт и
полное воспроизведение до EOF в Fuse. Все **25 326 AY-записей** и
**6733 runtime-сектора** совпали, повторов чтения нет. Все 16 КиБ таблиц
каждого диска проверены после настоящего Z80-bootstrap с подменённой ROM.
В Fuse проверяются 80 байтов экрана каждого кадра, а не каждый пиксель;
все компактные кадры целиком проверены скалярным декодером. Физический
привод и непрерывная смена носителей в одном Fuse-сеансе не проверялись.

| Том | Фактические кадры/с | Промахи номинальных сроков | Пропуски полей AY | Максимальное отклонение |
|---|---:|---:|---:|---:|
| 1 | 7,916807 | 1564 | 512 | 10,335625 с |
| 2 | 7,373636 | 1292 | 1010 | 20,291415 с |
| 3 | 7,177453 | 1298 | 1279 | 25,669137 с |

Всего **4154 промаха**, **2801 пропуск поля AY**, **2752 опустошения
очереди AY**. Пять восстановлений по IRQ-счётчику первого диска не являются
возвратом к фактическому графику OUT: при проверке реальных времён на каждом
диске остаётся одна невосстановленная серия отклонений, начиная с локального
кадра 61 / 4 / 2 (с нуля). Фактических восстановлений — **0 / 0 / 0**.
Ни точные сроки, ни резервный допуск в одно поле не пройдены.

Полные Fuse-интервалы включают ROM, модель вращения диска, IRQ и ULA;
искусственно вычитать из них «чистую механику» нельзя. Границы отличаются
от прежнего четырёхдискового опыта, поэтому это проверка работоспособности
и сроков нового комплекта, а не парное доказательство ускорения/замедления
всего проигрывателя только от таблиц Хаффмана.

**Решение:** ёмкость трёх дискет совместима с независимым запуском и точным
сохранением исходных кадров/AY-данных. Сохранить вариант как эксперимент;
не включать автоматически и не заменять корневые TRD до решения проблемы
сроков. Следующий полезный шаг — учитывать стоимость длинных Huffman-кодов
при выборе таблиц и оптимизировать полный тракт доставки кадра.

Данные: [поиск границ](volume_huffman_rebalance.json),
[полный Fuse](volume_huffman_fuse.json),
[фактическое восстановление сроков](volume_huffman_timing.json),
[индекс полных трасс](volume_huffman_evidence/index.json).

## Воспроизведение

Из корня рабочей копии, Python с NumPy и зависимостями проекта:

```powershell
python toolkit/probe_volume_huffman.py `
  --raw ../three-disk-quality/.tmp/lean_frame/stream.raw `
  --states ../three-disk-quality/.tmp/no_credits/source/conversion.npz `
  --zx0 ../audio-fidelity/.tmp/bin/zx0.exe `
  --read-cache ../three-disk-quality/.tmp/lean_frame/zx0/optimal `
  --read-cache ../startup-tables/.tmp/measure/zx0 `
  --output .tmp/probe --report toolkit/volume_huffman_probe.json
python toolkit/profile_volume_huffman.py `
  --probe toolkit/volume_huffman_probe.json --directory .tmp/probe `
  --states ../three-disk-quality/.tmp/no_credits/source/conversion.npz `
  --output toolkit/volume_huffman_cpu.json
python toolkit/rebalance_volume_huffman.py `
  --probe toolkit/volume_huffman_probe.json --directory .tmp/probe `
  --states ../three-disk-quality/.tmp/no_credits/source/conversion.npz `
  --zx0 ../audio-fidelity/.tmp/bin/zx0.exe --output .tmp/rebalance `
  --report toolkit/volume_huffman_rebalance.json
python toolkit/measure_volume_huffman.py `
  --probe toolkit/volume_huffman_probe.json `
  --partition toolkit/volume_huffman_rebalance.json --directory .tmp/probe `
  --states ../three-disk-quality/.tmp/no_credits/source/conversion.npz `
  --zx0 ../audio-fidelity/.tmp/bin/zx0.exe `
  --fuse 'C:/Program Files (x86)/Fuse/fuse.exe' `
  --read-cache .tmp/rebalance/zx0 --output .tmp/three `
  --report toolkit/volume_huffman_fuse.json
python toolkit/archive_deferred_disk.py --source .tmp/three `
  --summary toolkit/volume_huffman_fuse.json --output toolkit/volume_huffman_evidence
python toolkit/summarize_volume_huffman.py `
  --summary toolkit/volume_huffman_fuse.json --evidence toolkit/volume_huffman_evidence `
  --output toolkit/volume_huffman_timing.json
```

Пути `../…` относятся к соседним рабочим копиям в `.worktree`; можно
передать другие пути к входам с указанными SHA. Для другого количества
кадров нужно явно задать `--ends`.
