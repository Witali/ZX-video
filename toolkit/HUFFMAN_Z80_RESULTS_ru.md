# Полный Z80-прогон Хаффмана и двух стадий распаковки

18 сентября 2026, база `f3f5390`, полный фильм 4971 кадр. Изображение,
атрибуты, звук, разрешение и частота кадров не менялись. Взяты точные потоки
предыдущего [опыта Хаффман + ZX0](MOTION_ENTROPY_RESULTS_ru.md):

- FPR1 до Хаффмана: SHA-256 `843eb9756ef43927236207692a84075bc1c733012d5fccc5729eb113e8b59c24`.
- FPE1 с Хаффманом: SHA-256 `fd5eac0ebe023e0ceda403492483f34b8e5b404609d2317bed79953a59d00437`.

**Вывод:** первый декодер верен, но его нельзя целиком исполнять непосредственно
перед показом каждого кадра. На шести кадрах один Хаффман превышает весь
шестипрерывательный интервал, ещё до ZX0 и вывода изображения. Нужны
ограниченная по времени предварительная распаковка и дальнейшее ускорение.
Это не отказ от размера 2339165 байт; это ограничение проверенной реализации.

## Декодер по четыре бита

Все коды имеют длину не менее четырёх бит. Поэтому каждая порция из
четырёх бит завершает не более одного байта поправки. Статическая таблица
возвращает этот байт (0 означает отсутствие готового значения) и адрес
состояния для следующих четырёх бит. Настоящие поправки всегда ненулевые.

В таблице 254 состояния префикса, три столбца по 4096 байт:
значение, младший и старший байты адреса следующего состояния. Итого
**12288 байт**, код **76 байт**. Таблица строится на PC, а декодер Z80
только читает память, вращает/маскирует биты и записывает результат.
Он завершает группу по числу поправок из масок, не выдавая лишние
значения из нулевого дополнения последнего байта.

Входной указатель IX; основной HL — состояние таблицы; альтернативные
HL/BC — указатель результата и оставшееся число байтов. Эти регистры
потребуют явного сохранения при приостановке декодера. Совместимость
с IRQ/планировщиком этим изолированным прогоном не проверялась.

## Подсчёт T-states

Источник времён — [Zilog UM008011-0816](https://www.zilog.com/docs/z80/um0080.pdf).
Список с адресами и временами каждой команды сохранён в JSON. Независимая
формула проверяется при каждом исполнении группы:

```text
N = число выходных байтов
nibbles = ceil(число значащих битов / 4)
hi = ceil(nibbles / 2), lo = floor(nibbles / 2)

Хаффман, N > 0: 37 + 136*hi + 101*lo + 35*N - (10, если nibbles чётно)
Хаффман, N = 0: 27 T
Контроль LD A,B / OR C / RET Z / LDIR / RET: 21*N + 18 T; пустой — 19 T
```

Вход через IX стоит 29 T на байт. Подготовка старшего/младшего полубайта —
35/19 T, переход по таблице без результата — 72 T, готовый результат
добавляет 35 T относительно этого пути. Последний RET и переходы цикла
учтены в формуле. Загрузка источника и запись результата включены.
CALL, настройка регистров вызывающей стороной и загрузка таблиц исключены.

Полный Z80-прогон восстановил **1688733 поправки во всех 622 группах**.
Для сравнения через обычный LDIR пропущены те же байты результата.
Записи за пределы результата/стека запрещены проверяющим CPU;
контролируются граница источника, выходной буфер и возврат стека.

| Только получение байтов поправок | Всего T | Среднее T/кадр | Максимум T/кадр |
|---|---:|---:|---:|
| Копирование готовых значений | 35474591 | 7136,309 | 47961 |
| Хаффман | 362673773 | 72957,910 | 554488 |
| Добавка | +327199182 | **+65821,602** | +507847 |

Максимум добавки и Хаффмана относится к кадру с индексом 3685 (нумерация
от нуля); максимум копирования — к 4841. Время кадра измеряется между
выдачами последней поправки соседних кадров внутри группы. Подготовка
группы относится к первому кадру с поправками; пустая группа — к первому
кадру. Это распределение работы декодера, **не интервалы смены экранов**.

## ZX0 и суммарная работа двух стадий

Отдельно исполнен настоящий Z80 turbo ZX0 (126 байт кода) для всех
**615 блоков FPR1 и 565 блоков FPE1**, выход каждого побайтно сравнен
с соответствующим исходным блоком. Использованы сохранённые оптимальные
ZX0-блоки из измерений размера; новые варианты сжатия не подменяли их.

| Стадия | До, T на фильм | После, T на фильм | Разница среднего T/кадр |
|---|---:|---:|---:|
| Turbo ZX0 | 291270807 | 191504507 | −20069,664 |
| Выдача поправок в промежуточный буфер | 35474591 | 362673773 | +65821,602 |
| **Сумма отдельных стадий** | **326745398** | **554178280** | **+45751,938** |

Сумма в среднем растёт **65730,315 → 111482,253 T/кадр**, разница
**+227432882 T на фильм**. Хаффман уменьшает работу ZX0, но пока добавляет
больше собственной работы. Операция восстановления пикселей 117 T из
предыдущего опыта в эти числа **не входит**.

Это сравнение двух измеренных стадий с промежуточной записью, не готовых
проигрывателей. Будущий проигрыватель может читать/применять поправку без
такого копирования; его фактические расходы потребуется пересчитать.
Не измерены совместное исполнение, разбор заголовков/масок, движение,
рисование, AY, приостановка ZX0, подкачка, paging, IRQ, ULA, ROM и диск.

Размер видео прежний: **2470635 → 2339165 байт**, −131470. Округление
одного непрерывного видеопотока до секторов даёт 9651 → 9138, −513;
это **не** реальное размещение файлов по дискетам. Со старым замером AY
2416861 байт, превышение бюджета трёх TRD **479197 байт** до накладных расходов.

## Худшие кадры и память

Проектный интервал Spectrum 128 — 6×70908 = **425448 T** (как в проверках
Fuse выпуска). Хаффман один превышает его на индексах
**192, 3375, 3635, 3685, 3686, 4841**. Максимум 554488 T означает,
что синхронная схема уже не укладывается до добавления остальных стадий.
Среднее время это ограничение не отменяет.

Самая тяжёлая группа 581: 8 кадров, 10551 выходной байт, 9425 входных
байтов Хаффмана, **2603037 T** только на эту распаковку. Группа входа
больше 8-КиБ истории ZX0: нельзя считать, что всю группу удастся сразу
передать этому декодеру из существующего буфера. Нужен возобновляемый
читатель через границы блоков и ограниченная очередь результата.

Карта **измерительного стенда**, не выпуска:

| Данные | Адреса |
|---|---|
| Код Хаффмана | 8000h, 76 байт |
| Его вход группы | 4000h–7FFFh |
| Его результат | 9000h–BFFFh |
| Стек | 8FF0h, возврат 2 байта ниже |
| Таблицы | C000h–EFFFh, банк 6 |
| Отдельный ZX0: код / результат / вход / стек | 8000h / 6000h–7FFFh / A000h–DFFFh / 9FF0h |

Стенд переиспользует области экрана и рабочего пространства, поэтому не
подтверждает совместную карту 128 КиБ. В будущем таблица могла бы заменить
один 16-КиБ банк дискового кольца, но доставка при уменьшенном кольце ещё
не проверена; такая переразметка **не принята**. При следующей интеграции
нужно учесть два экрана, компактную историю, маски/векторы, очереди,
ZX0, код, AY/IRQ, стеки и TR-DOS одновременно.

## Проверки и решение

- Все поправки и оба набора ZX0-блоков восстановлены настоящими
  машинными командами в проектном интерпретаторе; формула времени
  Хаффмана совпала с каждым из 622 исполнений.
- 4 новых теста: явно заданные полубайты, пустые кадры, все значения
  алфавита фильма и разные окончания, случайная последовательность,
  неподходящие деревья. Добавленный SET проверен для всех битов,
  регистров/`(HL)`, значений и двух комбинаций Z/C — 32768 команд.
- 5 прежних тестов проигрывателя (включая IRQ и точные времена) и
  2 прежних теста циклических вращений/CPL прошли; всего 11 тестов.

**Решение:** сохранить прототип и измерения. Не встраивать его как
синхронную распаковку перед кадром. Следующий этап — приостановка по
небольшой квоте результата, сохранение состояния, чтение через границы
ZX0 и измерение очереди на тяжёлых участках, одновременно с ускорением
табличного разбора. PLAYER/TRD не менялись, встроенный горячий путь **0 T**.
Нового Fuse/дискового прогона нет; выпуск на трёх дискетах и его 8⅓ fps
по-прежнему не подтверждены.
