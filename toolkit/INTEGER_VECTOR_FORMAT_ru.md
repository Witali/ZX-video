# Отдельный опыт: целочисленные контуры и однотонные заливки

20 сентября 2026, ветка `codex/vector-contours`, база `2b3b4ce`.
Текущий проигрыватель сохранён. Это новый экспериментальный формат данных,
**не новый TRD-проигрыватель**. Цель — проверить предложение пользователя
о контурах/заливках, сохраняя прежние разрешение, изображение и AY.

## Что выполняет ПК, а что должен выполнять Spectrum

ПК ищет области, обходит границы и упрощает их. Контуры строятся до
экранного дизеринга, в существующей сетке 128×72 активных логических точек;
на экране остаются прежние 256×144 пикселя и чёрные поля. Это не новое
уменьшение разрешения. Четыре значения — уровни двухбитового изображения;
цвета Spectrum сохраняются отдельными атрибутами знакомест, а не заменяются
четырьмя глобальными цветами.

Первый исполняемый на ПК формат использует только прямые отрезки с
целочисленными вершинами. Включены внешний контур, отверстия, вложенные
области, тонкие линии и отдельные точки. Поиск областей и OpenCV
`approxPolyDP` работают только при конвертации на ПК. Spectrum не должен
искать контуры, вычислять кривые Безье или оперировать вещественными числами.

Растеризация эталона целочисленная: пересечения рёбер с центрами строк,
полуоткрытые границы, сортировка пересечений и попарная заливка. Для Z80
деление на каждой строке потребуется заменить прибавлением целой части
наклона и накоплением остатка. Начальные параметры ребра можно вычислить
на ПК. Пока это описание будущего потребителя, не измеренный код Z80.

## Три проверяемых представления

1. **Grid:** точные контуры по углам пикселей; удалены только вершины на
   одной прямой. Все отверстия сохранены. Ошибок геометрии быть не должно.
2. **Polygon:** контуры упрощены с допуском 0,5 или 1 логическая точка;
   выбирается меньшая запись. Затем все ошибки исправляются короткими
   горизонтальными растровыми заливками. Конечное изображение точно.
3. **Hybrid:** для каждого кадра выбирается меньшая несжатая запись из
   Polygon, прямоугольников изменений к экрану n−2 и полного двухбитового
   растра. Это простой локальный критерий, не оптимизация результата ZX0.

Чистый линейный рисунок без исходных заливок не считается эквивалентом
фильма: он меняет изображение. Для узких линий контур сохраняет их точную
площадь; специализированная команда STROKE с толщиной пока не реализована.
Растровые исправления внутри Polygon — предусмотренный гибрид для деталей,
а не разрешение удалять неудобные элементы.

## Экспериментальный IVC1

Заголовок: ASCII `IVC1`, ширина/высота/число кадров — три u16 little-endian.
Каждый кадр: u32 длина тела, шесть неизменённых AY-записей, атрибуты,
команды пикселей. Тело может превышать старое окно FAP3 4704 байта:
старый парсер этот формат не принимает.

Атрибуты относятся к экрану n−2. Режим 0: все 576 активных значений;
режим 1: u16 число диапазонов, каждый содержит u16 начало, u8 длину и
байты значений. Выбирается меньший вариант. Верх/низ остаются неизменными.

| Режим пикселей | Поля |
|---|---|
| 0: растр | 2304 байта активных двухбитовых значений |
| 1: изменения прямоугольниками | u16 количество; записи x,y,w,h,уровень по пять u8 |
| 2: контуры | u8 фон; для каждого из трёх других уровней u16 число контуров; у контура u16 число вершин и пары u8 x,y; затем u16 число исправлений и записи x,y,w,уровень |
| 3: контуры по сетке, компактно | вместо списка вершин: u16 число команд, первая точка x,y и байты «2 бита направления + 6 бит длины минус один»; контур замкнут |
| 4: короткие дельты вершин | первая точка x,y; затем dx/dy −7..+7 по одной тетраде байта; FF означает следующие абсолютные x,y |

Координаты вершин находятся на углах логических пикселей: x=0..128,
y=0..72. Размеры и координаты помещаются в байты; длины списков — u16.
Для контуров применяется правило чётности всех пересечений одного уровня,
поэтому направление обхода не используется для определения отверстий.
Прямоугольники и исправления заполняют полуоткрытые диапазоны.

Режимы 3/4 проверяются второй итерацией без повторного поиска контуров.
Они меняют только запись тех же координат и сохраняют все исправления.
Гибрид заново выбирает между 3/4, прямоугольниками и растром. Смещения
между вершинами одного контура ещё не являются межкадровым сжатием фигур.

## Вывод и память

Целевой потребитель строит изображение прямо в скрытом экранном банке 5/7.
В срок IM2 только переключает экран. Отдельной полной копии готового кадра
не вводим. Однако полная заливка фона и последующие заливки областей могут
записывать одни байты несколько раз: это надо учитывать при сравнении.

Простой эталон хранит списки пересечений на ПК. Их нельзя считать бесплатной
RAM Spectrum. Для реализации следует сравнить:

- список активных рёбер с ограниченным числом элементов;
- подготовленные ПК монотонные многоугольники/трапеции, где на строку
  приходятся только левая и правая границы;
- прямоугольники и заранее подготовленные горизонтальные диапазоны.

Преобразование вершин в рёбра/трапеции может увеличить поток, зато упростить
декодирование. Адреса стеков, AY, экранов, таблиц, очередей и TR-DOS нужно
разместить явно в 128 КиБ. Переход на меньшее дисковое кольцо без проверки
устойчивой подачи не принимается.

## Проверки и критерий выбора

Каждая из трёх версий сериализуется, заново разбирается и восстанавливает
изображение/атрибуты двух чередующихся экранов. AY проверяется по байтам.
Покадровый отчёт содержит число вершин, контуров, пересечений по строкам,
заливок и ошибок до/после растровой коррекции. Искажения упрощённого контура
без исправлений показаны только как диагностика; это не разрешённое качество
нового выпуска. Выбранные трудные сцены вынесены в контактный лист.

Тесты покрывают пустой/полный фон, вложенные отверстия, диагональные касания,
шахматное поле, тонкие линии, случайные области, диагональные рёбра,
все режимы данных и атрибутов. Четыре теста проходят; численные результаты
полного прогона и сжатия приведены ниже.

Контактный лист просмотрен: кадры 12, 408, 2858, 3009, 3686, 3685.
Средняя колонка показывает геометрию пробного полигона даже там, где
гибрид выбирает растр. Справа — диагностика до точных исправлений,
а не конечное качество. На сценах с мелкими фрагментами видно множество
малых областей; контурное представление требует большого числа вершин.

DEFLATE в отчёте — только быстрый отбор раскладки. Настоящий ZX0 измеряется
отдельно блоками 8192 байта с независимой проверкой распаковки. Объём данных
не доказывает ни размещение загрузчика на трёх дисках, ни 8⅓ кадра/с.
В этом опыте hot path существующего проигрывателя не изменён: **0 T разницы**.
Новый rasterizer Z80, его абсолютные T, ULA/ROM/диск и полное расписание
ещё не проверены. Победитель по общей эффективности заранее не назначается.

## Полный опыт: 4221 кадр без титров

Источник — `movie_no_credits.json`, история и сцена после титров сохранены.
Проверены все 4221 кадр и 25326 обновлений AY. Для каждой версии нулевые
ошибки активных пикселей, атрибутов и AY; версия с компактными координатами
также проверена на всех кадрах. Прогоны относятся к представлению данных
на ПК. Проигрывание с точными дедлайнами 120 мс ими не подтверждается.

Несжатые потоки включают кадры, атрибуты и исходный звук:

| Представление | Байты до ZX0 |
|---|---:|
| База FAP3 | 3 097 959 |
| Точные контуры по сетке | 23 375 323 |
| Упрощённые полигоны с точными исправлениями | 19 226 193 |
| Первый гибрид: полигоны / прямоугольники / растр | 7 453 649 |
| Контуры по сетке, направление и длина | 15 064 969 |
| Полигоны, короткие смещения вершин | 15 940 981 |
| Гибрид с компактными контурами | 7 396 678 |

Настоящий ZX0 v2, optimal, блоки по 8192 байта, тот же исполняемый encoder,
включены четыре байта заголовка каждого блока:

| Представление | Блоки | Байты с ZX0 | К базе |
|---|---:|---:|---:|
| База FAP3 | 379 | 1 932 429 | — |
| Первый гибрид | 910 | 3 468 203 | +1 535 774 / +79,47% |
| Гибрид с компактными контурами | 903 | 3 476 798 | +1 544 369 / +79,92% |

Все 1813 блоков двух новых потоков независимо распакованы и сверены.
Во второй попытке запись до ZX0 стала меньше на 56971 байт, но результат
ZX0 вырос на 8595 байт. Короткая запись отдельной вершины не гарантирует
лучшее сжатие всего потока.

**Решение:** сохранить код и результаты в отдельной ветке, основной формат
не заменять. Даже лучший из этих двух потоков больше суммарных 1966080 байт
трёх целых TRD. Нижняя граница — шесть образов, ещё без файловой системы,
загрузчика и разделения частей; шесть рабочих дисков этим опытом не созданы.
Нет смысла переносить именно этот вариант в Z80-плеер ради цели трёх дисков.
Вывод относится к проверенным форматам, а не ко всем векторным кодекам.

В первом гибриде полигоны выбраны в 69 кадрах, прямоугольники — в 2357,
растр — в 1795. Во втором — 182 кадра с контурами по сетке, 48 с полигонами,
2300 с прямоугольниками и 1691 с растром. Выбор делается по длине записи
до ZX0, поэтому это **не предел возможностей гибридного кодека**.

Упрощённые полигоны имеют в среднем 1150,23 вершины, максимум 3808;
точные сеточные контуры — в среднем 2476,01. Упрощение требует исправить
в среднем 504,30 логической точки. При построении полного кадра полигонами
получается в среднем 8964,59 обращений к байтам native-экрана, максимум
11298, включая очистку активных 4608 байт. Это счётчик записей выбранного
алгоритма, **не измерение CPU**; он относится ко всем полигональным кадрам,
а не только к кадрам, выбранным гибридом.

Максимальная полигональная запись — 10400 байт. Для неё старого окна
пакета 4704 байта недостаточно: потребитель должен разбирать запись
потоком или иметь другую очередь. Это ещё одна причина считать память
и время полного конвейера, а не только компактность одной вершины.

## Что стоит развивать дальше

Первая реализация описывает фигуры заново в каждом кадре. Следующий опыт
должен проверять именно повторное использование геометрии во времени:

1. На ПК сопоставить области соседних кадров, присвоить устойчивые ID.
   Для неизменной фигуры хранить только ID, для перемещения — ID и dx/dy,
   для деформации — изменения части вершин. Поиск соответствий не переносить
   на Spectrum. Считать размер таблицы фигур в бюджете 128 КиБ.
2. Разделить статичный фон и движущиеся фигуры. Для экрана n−2 определить
   области, которые надо восстановить после движения, и порядок заливок.
   Старое положение фигуры нельзя просто оставить на скрытом экране.
3. Выбирать команды по участкам: большие однотонные области — векторы,
   мелкие детали — текущие растровые дельты. Считать итог с ZX0, а не только
   длину отдельной команды до сжатия.
4. Лишь после выигрыша по данным реализовать ограниченный набор заливок
   на Z80, посчитать абсолютные T и сравнить полную подачу кадров с базой.
   Включить очистку, повторные записи, атрибуты, paging, AY и дисковое чтение.

Временная стабильность контуров обязательна: нельзя уменьшать размер ценой
дрожания силуэтов. Малозаметное упрощение без точных исправлений — отдельный
опыт с покадровым контролем качества; оно не измерено этим lossless-прогоном.

## Источники метода

Обход границ по углам пикселей и разделение tracing на контуры и полигоны
описаны у [Peter Selinger, Potrace](https://potrace.sourceforge.net/potrace.pdf).
Здесь реализован собственный дискретный обход; сглаживание Безье Potrace
не используется. Упрощение выполняет документированная функция
[OpenCV approxPolyDP](https://docs.opencv.org/4.13.0/d3/dc0/group__imgproc__shape.html).
Растеризатор и двоичный формат написаны для этого эксперимента.
