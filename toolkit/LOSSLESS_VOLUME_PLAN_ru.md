# Уменьшение полного комплекта без потери качества

Текущее поручение пользователя: получить **две или три дискеты с ZX0**,
сохраняя изображение и звук. База — выпуск из 30 TRD, коммит `55a337e`.
Уменьшенные чёрно-белые профили из оценки одной дискеты не применяются.

## Неизменные данные

- Все 4971 цветной экран текущего выпуска, побайтно.
- Все 29826 состояний AY, включая шум, на частоте 50 Гц.
- Видео 25/3 кадра/с, полная длительность 596,52 с.
- SHA-256 компактного видео:
  `60920116d2cbcb147cb066fe10601b7a6837a3dbc70276e930d0320c045091c9`.
- SHA-256 звуковых состояний:
  `c55ee9d570284c89a33bd582eb28f3c141676ec63e7ced4c00b5aac7cb575cae`.

## Работа

Целевой бюджет трёх обычных TRD — не более 1 937 664 байт потока
до учёта дополнительных заголовков, зазоров интерливинга и роста проигрывателя.
Для двух — 1 291 776 байт. Плотная существующая упаковка ZX0 требует
3 875 046 байт; изменение представления кадров необходимо.
`probe_lossless_layouts.py` проверяет обратимые преобразования полного
массива экранов: XOR с предыдущими кадрами, вычитание, битовые плоскости,
код Грея, плитки и перестановку по времени. DEFLATE служит только быстрым
отбором; выбранные варианты необходимо измерить настоящим ZX0.
Размер офлайн-архива не доказывает возможность воспроизведения на Z80.

Предыдущие промежуточные эксперименты (не выполнение цели 2–3 дискет):

- Порог 1400, максимум 512 кадров на том и запас планировщика 80:
  20 томов, 4 511 582 байта блоков. Полные Fuse и CPU-проверки пройдены;
  максимум интервала кадра 122,819927 мс. Средняя подготовка кадра:
  foreground 120 130,176 T + background 70 839,633 T = 190 969,810 T.
- Те же параметры с `--separate-stored`: 19 томов, 4 366 047 байт.
  Fuse дошёл до конца всех 4971 кадров, но максимум 129,119231 мс
  превышает порог 125 мс. Этот комплект не принят в выпуск.
- Бинарный PLAYER обоих опытов совпадает с выпуском, 5120 байт,
  SHA-256 `e70a0c7576c109979187a1b94edcac97a454b01d24a6ca99bf6262864cfff3fa`.
  Стоимость каждой инструкции до/после одинакова, разница 0 T.
  Для сравнения, средняя суммарная подготовка кадра выпуска —
  190 841,623 T: вариант на 20 томах требует на 128,186 T больше.
  Это CPU без ROM/IRQ/ULA; дисковые задержки входят отдельно в замер Fuse.

В ответ на уточнение пользователь **подтвердил сохранение качества и
8⅓ кадра/с**. Снижение кадровой частоты для достижения трёх дискет
не разрешено. Сохранены 48 вариантов обратимой раскладки, три варианта
компенсации движения, 12 вариантов масок изменений и четыре перестановки
битов по времени. Их итоговые размеры
находятся в `lossless_*_measurements.json`; отчёты ZX0 с `complete: true`
содержат SHA-256 и проверку каждого распакованного блока.
Частичные прогоны хранятся среди игнорируемых экспериментальных сборок.

1. Проверено влияние квоты чтения без изменения потока. Квоты 4 и 6
   уже не устранили сбой длинного тяжёлого участка: AY пуст перед кадром
   2929. Они не принимаются как исправление. Скрипт `retune_read_quota.py`
   меняет только операнд LD DE,nn. Добавление долга: 115 T без насыщения,
   114 T с насыщением, до/после одинаково, разница 0 T. Полное время
   чтения и ветвления проверяется отдельно в Fuse.
2. Запас офлайн-планировщика границ томов снижен с 160 до
   80 секторов в эксперименте на 20 томах. Рабочий резерв проигрывателя остаётся
   64 сектора; расчёт упаковки не является доказательством устойчивости.
3. Добавлено разделение групп тяжёлых кадров, хранимых без внешнего ZX0,
   и групп лёгких кадров. Выигрыш упаковки подтверждён, но вариант на
   19 томах превышает допустимый интервал кадра.
4. Для ускорения опытов общие видеопакеты кодируются один раз: при новой
   границе тома заново нужны лишь первые два пакета. Дальше истории банков
   n−2 и видимого экрана n−1 совпадают. Проверять равенство старому методу.

## Результат поиска представления без потерь

**Цель 2–3 дискеты пока не достигнута.** Все размеры ниже относятся
к полному видео и не включают звук, загрузчик, новый декодер и размещение
по секторам. Восстановление исходных данных проверено.

| Представление | Архиватор / блок | Байт видео |
| --- | --- | ---: |
| Маски изменённых байтов + значения, раздельно | оптимальный ZX0 v2, 8192 байта | 2 894 676 |
| Байты, перестановка по 32 кадрам | ZX0 v2 `-q`, 32768 байт | 2 942 153 |
| То же представление | DEFLATE, весь поток | 2 715 082 |
| Байты, перестановка по 32 кадрам | DEFLATE, весь поток | 2 742 980 |
| Компенсация движения плитками 8×8 | DEFLATE, весь поток | 2 952 319 |

Даже первый вариант превышает бюджет трёх TRD на **957 012 байт**
до добавления звука. Прежний независимый замер неизменённого звука с ZX0
даёт ещё 77 696 байт (блоки 6138 байт, `single_disk_measurements.json`).
Получается 2 972 372 байта без дисковых заголовков: для трёх дискет нужно
убрать ещё около 34,8%. Это результат проверенных способов, а не
математическое доказательство невозможности более сильного алгоритма.

Эти новые представления ещё не поддерживаются Z80-проигрывателем.
Временная перестановка на 32 кадра также требует другого распределения
памяти и расписания распаковки. Сам по себе размер архива не доказывает
ни число играбельных дискет, ни сохранение 8⅓ кадра/с.

Следующий рубеж — найти обратимое представление, которое с **ZX0**,
полным звуком и запасом на служебные данные укладывается в 1 937 664 байта.
Только после этого реализовывать соответствующий Z80-декодер и проверять
полный комплект по условиям ниже. Существующий проигрыватель не заменён
офлайн-прототипом.

## Воспроизведение замеров

`CHECKPOINT` — `source/conversion.npz` полной сборки; `AUDIO` —
`audio/50Hz/raw.bin`. Скрипты проверяют SHA-256 принятых экранов и звука.
Пути к локальным инструментам задаются явно; исходник не загружается заново.

```text
python toolkit/probe_lossless_layouts.py --checkpoint CHECKPOINT --audio AUDIO --output toolkit/lossless_layout_measurements.json
python toolkit/probe_motion_layout.py --checkpoint CHECKPOINT --output toolkit/lossless_motion_measurements.json --cache .tmp/motion_probe
python toolkit/probe_sparse_planes.py --checkpoint CHECKPOINT --output toolkit/lossless_sparse_measurements.json --cache .tmp/sparse_probe
python toolkit/probe_sparse_planes.py --checkpoint CHECKPOINT --output toolkit/lossless_sparse_measurements.json --cache .tmp/sparse_probe --verify-only
python toolkit/probe_zx0_storage.py --raw .tmp/sparse_probe/packed_8_separate.raw --block-bytes 8192 --zx0 ZX0 --cache .tmp/zx0_probe --output toolkit/lossless_zx0_sparse_measurements.json
python toolkit/probe_lossless_layouts.py --checkpoint CHECKPOINT --audio AUDIO --layouts packed --predictions absolute xor1 --orders timebits8 timebits32 --cache .tmp/timebits --output toolkit/lossless_temporal_bits_measurements.json
python toolkit/probe_zx0_storage.py --checkpoint CHECKPOINT --layout packed --prediction absolute --time-group 32 --block-bytes 32768 --quick --zx0 ZX0 --cache .tmp/zx0_probe --output toolkit/lossless_zx0_time_measurements.json
```

ZX0 проверен независимым декодером для каждого блока; режим `--quick`
явно отмечен в отчёте и использует отдельный кэш от оптимального режима.
Все 12 файлов масок/значений дополнительно прочитаны с диска и восстановлены
по полному потоку до 4971 экранов. Общий набор тестов: 115 пройдено.

## Условия принятия

Все экраны и AY должны совпасть в CPU-валидаторе, все реальные записи
AY — в трассе Fuse. Нельзя принимать недогрузки или потерянные такты ради
уменьшения размера. Интервалы кадров — до 125 мс, звуковых тактов — до
25 мс в проверенном Fuse; метрики звука сравнивать с той же дорожкой.
При изменении Z80 записать абсолютные T-states и разницу, отдельно от ROM,
ULA, IRQ и дисковых задержек. Изменение только упаковки не меняет стоимость
инструкций существующего декодера, но меняет частоту исполнения его путей.

После полной проверки заменить комплект в корне, удалить лишние старые
части, записать образы через Git LFS и отправить коммиты. До успешной
проверки выпуск из 30 дискет остаётся доступен.
