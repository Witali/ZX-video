# FAP3: отложенное чтение и обслуживание диска после кадра

24 сентября 2026; база `7aca091`. **Эксперимент, не новый выпуск.**

## Результат

Отложенное чтение с проверкой обслуживания после каждого кадра ускоряет
первую часть с **7,9194 до 8,0389 кадра/с**. Во всех четырёх частях исчезли
повторные чтения, появившиеся в первых вариантах отложенной подкачки.
Однако тяжёлые сцены всё ещё опаздывают, AY не выдерживает каждый физический
50-Гц интервал. Ни точные сроки, ни резервный допуск 20 мс не выполнены.
Количество дискет осталось **четыре**; цель не более трёх ещё не достигнута.

Метод сохраняет данные FAP3 и AY. Параметры общего конвертера и корневые
TRD не заменены экспериментальным режимом. Полный совместимый H.263 здесь
не вводится; оценка простых блочных методов — в [отдельном отчёте](LIGHT_VIDEO_CODECS_ru.md).

## Как работает очередь чтения

Раньше освобождение каждого полного 256-байтового сектора сразу вызывало
чтение следующего. Теперь потребитель начисляет один свободный сектор
счётчику `pending`, только когда все его байты уже скопированы во входное
окно ZX0. Во время ожидания публикации плеер читает по одному сектору.
Если очередь достигает `deferred_limit`, чтение выполняется принудительно.
Лимит 248 оставляет не менее восьми загруженных секторов в кольце 64 КиБ.
Учитываются и четырёхбайтовые заголовки блоков, и переходы между банками.

Один дополнительный вызов после каждого опубликованного кадра проверяет
время с последнего обслуживания. После 64 полей он читает один ожидающий
сектор; если очередь пуста, вызывает SEEK+HLD на последний прочитанный
цилиндр. Секторные курсоры, сторона диска и флаги READ при этом не меняются.
Вычитание 16-битного счётчика проверено также через его переполнение.
Публикация готового экрана остаётся в IRQ, с исходными абсолютными сроками.

## Неудачные промежуточные варианты

1. **Только отложенное чтение, лимиты 64/248.** Длинные участки без чтений
   оставляют привод без обслуживания. В трассе обнаружен промежуток
   14 794 589 T, около 4,17 с, после которого короткое чтение требует
   полного повторного вызова ROM. Такой вызов достигает примерно 5,31 млн T
   вместо обычного порядка 30 тыс. T. Скорость хуже базы.
2. **Поддержание активности только в свободном ожидании, 64 поля.**
   Повторные чтения остаются: на тяжёлых кадрах свободного ожидания нет,
   поэтому эта проверка долго не вызывается.
3. **Та же проверка после каждого кадра.** Во всех восьми полных прогонах
   частей для лимитов 64/248 повторные чтения исчезли. Средняя скорость
   выросла, но перегрузка тяжёлых сцен и пропуски физических AY-полей остались.

Первый запуск CPU-фикстуры обнаружил незаданный кэш дорожки ROM в стенде;
инициализация `5CF5/5CF6/5CFA` приведена в соответствие с bootstrap.
Это исправление стенда, не результат измерения размера или скорости плеера.

## Полные измерения Fuse

Скорость считается по фактическим OUT переключения экрана:
`(число кадров − 1) × 3 546 900 / (T последнего OUT − T первого OUT)`.
Она не включает стартовую загрузку и время человека на смену дискеты.
Загрузка и полный интервал воспроизведения отдельно сохранены в JSON.

| Вариант | FPS частей 1 / 2 / 3 / 4 | Пропущено физических AY-полей, сумма | Кадров вне номинального срока, сумма | Повторных чтений |
|---|---|---:|---:|---:|
| База, немедленное чтение | 7,9194 / 7,7212 / 6,9072 / 7,2891 | 2939 | 4096 | 0 |
| Очередь 64 | 7,8752 / 7,6513 / 6,8478 / 7,2254 | 3162 | 4034 | 4 |
| Очередь 248 | 7,8073 / 7,6822 / 6,7895 / 7,2102 | 3254 | 4036 | 7 |
| Очередь 64, обслуживание в ожидании | 7,8723 / 7,6524 / 6,8478 / 7,2254 | 3164 | 4057 | 4 |
| Очередь 248, обслуживание в ожидании | 7,8093 / 7,6778 / 6,7906 / 7,2102 | 3255 | 4015 | 7 |
| Очередь 64, обслуживание также после кадра | 7,9502 / 7,7370 / 6,9261 / 7,2933 | 2872 | 3942 | 0 |
| Очередь 248, обслуживание также после кадра | 8,0389 / 7,7629 / 6,9150 / 7,3624 | 2686 | 3873 | 0 |

Лимит 248 даёт лучший общий результат, хотя на третьей части 64 немного
быстрее. Ни один вариант не проходит временные требования выпуска.
Число поздних кадров по счётчику IRQ и отклонения фактических OUT записаны
раздельно. При оценке OUT используется прежняя погрешность 64 T на фазу
инструкций внутри IRQ; она не скрывает целое поле 70 908 T.

| Часть | Поздних кадров: база → очередь 248 с проверкой после кадра | Максимальное отклонение OUT, с: база → новый | Восстановленных серий опозданий: база → новый |
|---|---:|---:|---:|
| 1 | 1215 → 1134 | 8,4964 → 5,9975 | 5 → 4 |
| 2 | 1021 → 880 | 10,5156 → 9,4960 | 5 → 2 |
| 3 | 843 → 842 | 21,9307 → 21,7308 | 0 → 7 |
| 4 | 1017 → 1017 | 18,1723 → 16,7729 | 1 → 3 |

В каждой части обоих вариантов остаётся одна невосстановленная серия
опозданий до конца части. Улучшение средних FPS не означает отсутствие
накопленного отставания. Все номера кадров и серии сохранены в полном архиве.

## Такты Z80 и память

Стенд исполняет инструкции и сверяет цену каждой с таблицей ассемблера
([Zilog Z80 User Manual](https://www.zilog.com/docs/z80/um0080.pdf)). Здесь
**исключены** тела ROM, механика диска, IRQ и ULA contention. Они учитываются
в полном времени Fuse. Нельзя складывать эти два измерения или объявлять
их разность чистой задержкой механики.

| Путь | База, T | Новый, T | Разница / условие |
|---|---:|---:|---|
| Сектор ещё не освобождён | 28 | 38 | +10, дополнительный JP |
| Полный сектор после EOF | 74 | 84 | +10 |
| Сектор освобождён, чтение отложено | 907 при немедленном чтении | 124 | −783 сейчас; чтение ещё предстоит |
| Принудительное чтение на той же дорожке | 907 | 1007 | +100 без отметки времени |
| То же, с отметкой времени | 907 | 1039 | +132 |
| Чтение из ожидания, с отметкой времени | — | 1123 | +31 T на вызов и проверку результата таймером |
| Пустая очередь, обслуживание ещё не требуется | — | 164 | +31 T снаружи, если вызвано из ожидания |
| Проверка после кадра, обслуживание ещё не требуется | 0 | 137 + 17 | **+154 T/кадр** |
| После кадра: нужен SEEK, прошло 64 поля | 0 | 597 + 17 | **+614 T**, дополнительно тело ROM/диск |
| После кадра: нужен SEEK, прошло 256 полей | 0 | 576 + 17 | +593 T; более короткая ветвь проверки |
| После кадра: нужен ожидающий сектор | — | 1273 + 17 | 1290 T; включает чтение и отметку времени |
| Стартовое копирование 256 байтов | 0 | 5401 | +5401 только при запуске тома |

Обычное отложенное чтение оплачивает и 124 T постановки в очередь, и
1123 + 31 T обслуживания: **1278 против 907 T**, +371 T на сектор,
не считая остальных проверок. Выигрыш получен переносом I/O в свободное
время, а не уменьшением числа служебных инструкций. Цена чтения на границе
дорожки или банка отличается; этот микрозамер относится к общей ветви
на той же дорожке, полные прогоны включают все границы.

Сохраняется [раскладка всех 128 КиБ](PIPELINED_FRAME_ru.md#раскладка-128-киб):
банки 0/1/3/4 — кольцо 64 КиБ; 6 — Huffman; 5 — основной экран,
TR-DOS workspace, компактный кадр, кэш и код; 2 — код, таблицы, стеки,
AY, входное окно и IM2; 7 — второй экран, парсер/таймер и история ZX0.
Нового кадрового или дискового буфера нет. Дополнительный код использует
уже отработавший bootstrap `6100..61FF`, до надписи следующего диска `6200`.
Счётчики занимают 3 байта; программа с состоянием заканчивается перед `61FE`.
Временная копия лежит в ещё пустой AY-очереди `A200..A2FF` и переносится
до `audio_init`. Драйвер получает 11 байтов кода; копирование —
`3 × 10 + (21 × 256 − 5) = 5401 T`. Стек диска и workspace ROM прежние.

## Что проверено

- Все семь вариантов: **29 547 опубликованных кадров, 177 282 записи AY,
  45 612 успешно прочитанных runtime-секторов**, 28 завершённых прогонов частей.
- Все AY-записи и все 256 байтов каждого успешно прочитанного runtime-сектора
  сравнены с источником. Для видео Fuse сравнивает **80 байтов каждого кадра**,
  это не полное сравнение экранной RAM. Данные кодека в опыте не менялись.
- Микростенд: 12 сочетаний лимита/ожидания/раскладки, по 230 400 точных
  входных байтов и 1544 запроса, многократные переходы кольца и банков;
  641 сочетание дорожки/времени/EOF для обслуживания, также чтение из очереди.
- 18 тестов общего конвертера, дискового адаптера и кадрового конвейера прошли.
  Сохранение прежнего машинного кода при выключенных опциях проверено.
- Все три перехода между томами: надпись, отказ чужому диску/серии,
  принятие правильного диска и bootstrap RAM проверены Z80-стендом с ROM mock.
  Загрузка каждого тома отдельно проверена полным Fuse-прогоном.
- Физический привод и реальная вставка дискет не проверялись. Это не выпуск.

заменить. Файл NPZ должен соответствовать указанному SHA компактных кадров.
Вход и cache прежних опытов читаются без изменения.

```powershell
$env:PYTHONPATH='toolkit'
$raw='C:/Work/ZX-video/.worktree/three-disk-quality/.tmp/lean_frame/stream.raw'
$states='C:/Work/ZX-video/.worktree/three-disk-quality/.tmp/no_credits/source/conversion.npz'
$zx0='C:/Work/ZX-video/.worktree/audio-fidelity/.tmp/bin/zx0.exe'
$fuse='C:/Program Files (x86)/Fuse/fuse.exe'

python toolkit/run_deferred_disk.py --raw $raw --states $states --zx0 $zx0 --fuse $fuse --read-cache $cache --output .tmp/deferred --report toolkit/fap3_deferred_summary.json
python toolkit/run_deferred_disk.py --raw $raw --states $states --zx0 $zx0 --fuse $fuse --read-cache $cache --limits 64,248 --keepalive-fields 64 --output .tmp/deferred-keepalive --report toolkit/fap3_deferred_keepalive_summary.json
python toolkit/run_deferred_disk.py --raw $raw --states $states --zx0 $zx0 --fuse $fuse --read-cache $cache --limits 64,248 --keepalive-fields 64 --frame-service --output .tmp/deferred-frame-service --report toolkit/fap3_deferred_frame_service_summary.json
python toolkit/benchmark_deferred_disk.py --keepalive-fields 64 --frame-service --output toolkit/fap3_deferred_frame_service_cpu.json
python toolkit/test_fap3_disk.py --volumes .tmp/deferred-frame-service/limit-248 --output toolkit/fap3_deferred_swap_checks.json
python toolkit/archive_deferred_disk.py --source .tmp/deferred-frame-service --summary toolkit/fap3_deferred_frame_service_summary.json --output toolkit/fap3_deferred_evidence/frame-service
python -m unittest test_generic_converter test_fap3_disk test_pipelined_frame -v
```

Fuse запускается строго последовательно из-за общего `stdout.txt` Windows.
Для первых двух CPU-отчётов убрать соответственно обе опции либо только
`--frame-service`. Архиватор применяется к трём каталогам по тому же образцу.
Обычный `profile_fap3.py` отвергает этот режим: его идеальный источник данных
не моделирует очередь свободных секторов и не должен выдавать ложный CPU-профиль.

**Решение:** сохранить опциональный режим и все неудачные промежуточные
замеры. Для дальнейшего продвижения нужны уменьшение затрат подготовки
тяжёлых кадров и размера данных; одной политикой подкачки цель не достигается.
