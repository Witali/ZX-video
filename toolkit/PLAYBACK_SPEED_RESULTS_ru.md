# Ускорение вывода: результаты первого этапа

15 сентября 2026 года. База — `014f819`, v8, `cpu-fields`, прежние команды
рисования. Выполнены работы по [плану ускорения](PLAYBACK_SPEED_PLAN_ru.md).
**Средняя скорость выросла с 5,107 до 6,143 кадра/с (+20,29%). Цель 25/3
кадра/с пока не достигнута.** Быстрый дисковый профиль экспериментальный:
проверен в Fuse с TR-DOS 5.03; реальный дисковод и восстановление после
ошибок чтения ещё не проверялись.

## Что реализовано

1. `--drawing registers`: маска восьми позиций хранится в A, временно в AF′;
   команды точек сохраняют адреса строк в BC/DE. Формат команд и все пиксели
   остаются прежними, дополнительные байты на дискете не требуются.
2. `--disk-reader trdos503`: после первого чтения на дорожке используется
   секторная процедура ROM напрямую. Полный диспетчер вызывается при смене
   дорожки. Убирается повторный READ ADDRESS для каждого сектора.
3. `--disk-layout interleaved`: последовательность чтения полных дорожек
   1, 9, 2, 10, …, 8, 16. Это отдельная версия потока **v9**. Сборщик учитывает
   незаполненные позиции последней дорожки при проверке вместимости.
4. `--pacing deadline`: общий срок следующего показа увеличивается на шесть
   полей, без сброса часов после каждого кадра. При отставании сохраняется
   подкачка: кольцо пополняется до 64 секторов или конца потока.
5. `--disk-reader trdos503-irq`: короткий IM2-обработчик и его стек размещены
   в фиксированной памяти без задержек ULA. Во время прямого секторного
   чтения прерывания разрешены; счётчик в HL′ продолжает идти.

Все режимы выбираются явно. Параметры по умолчанию сохранены. Серии чтений
`--read-batch 2|4|8|16` оставлены для экспериментов; они ограничены свободным
местом, банком, дорожкой и остатком потока. Быстрый читатель и чередование
секторов требуют `--read-batch 1`.

Данные потока и количество реально прочитанных секторов не выросли. Читается
2518 секторов с заголовком; из них 321 до первого кадра. Пять пустых позиций

обоих банков и девять регистров AY каждого кадра проверены побайтно
инструкционным валидатором. Fuse отдельно прошёл все 1000 кадров без входа
в `fatal` и обработчики недогрузки. Пиксели Fuse этим тестом не сравниваются.

## Точные такты Z80

Источник — [таблица команд Zilog UM0080](https://www.zilog.com/docs/z80/um0080.pdf).
Указаны CPU T-states без contention, ожиданий HALT и выполнения ROM.
Полное время доставки измерено отдельно в таблице выше. Сравниваются те же
ветви машинного кода; `N` — число изменённых позиций строки.

| Команда: от входа до `command_loop`, без диспетчеризации | До, T | После, T | Разность, T |
|---|---:|---:|---:|
| Маска строки | 2067 + 64N | 1287 + 68N | −780 + 4N |
| Список точек | 260 + 265N | 220 + 189N | −40 − 76N |
| Полный IM2, включая вход CPU и возврат | 88 | 61 | −27 |

Для маски неизменная подготовка занимает 329 T. Старый пропуск позиции:
`LD A,(nn)` 13 + `ADD A,A` 4 + `LD (nn),A` 13 + `JR NC` 12 + два `INC rr`
по 6 = 54 T. Новый пропуск: `ADD A,A` 4 + `JR NC` 12 + 12 = 28 T;
добавлены четыре загрузки масок по 13 T. Отсюда 2067 и 1287 T с конечным
`JP` 10 T. Изменённая позиция добавляет соответственно 64 и 68 T с учётом
непринятого перехода. Экономия на строке — от 652 до 780 T.

Команда точек экономит 40 T на сохранении двух указателей и 76 T на каждой
позиции за счёт удаления загрузок/сохранений адресов и номера столбца.
Новый ISR: `EXX` 4 + `INC HL` 6 + `EXX` 4 + `EI` 4 + `JP` 10 +
ROM `NOP; RET` 14 + вход IM2 19 = **61 T**, около 17,2 мкс.
HL′ зарезервирован для часов; обработчик сохраняет основные регистры и AF′.

Таблица транспорта получена `benchmark_playback_speed.py`; входящие
`CALL 3D13h` / `JP 3D2Fh` включены, выполнение процедуры ROM исключено.
Один сектор, банк кольца 1, адрес C000h, дорожка 3; чередование уже включено.

| Путь | До, T | После, T | Разность, T |
|---|---:|---:|---:|
| Инициализация часов | 5722 | 5635 | −87 |
| Чтение на той же дорожке, сектор 1 (с нуля) | 199 | 470 | +271 |
| То же, сектор 8 | 199 | 465 | +266 |
| Чтение с переходом 15 → 0 | 228 | 544 | +316 |
| Полный диспетчер при новой дорожке | 199 | 337 | +138 |
| Подкачка одного сектора вместе с чтением | 623 | 1093 | +470 |
| Подкачка при полном кольце | 85 | 73 | −12 |
| Подкачка после конца потока | 35 | 134 | +99 |
| Планировщик: кадр пора показывать, чтений нет | 198 | 205 | +7 |

Последняя строка включает в старом цикле один HALT как 4 T, без ожидания
прерывания. Новый цикл проверяет готовый срок. Рост расходов транспорта
окупается меньшим временем внутри ROM и меньшим дисковым ожиданием.
Средняя подготовка кадра экономит **22 636,002 T**, максимум — **2096 T**.
Все допущения и абсолютные значения сохранены в
[playback_speed_cycles.json](playback_speed_cycles.json).

## ROM, часы и память

Прямые адреса действительны для проверенной TR-DOS 5.03. SHA-256 ROM Fuse:
`91259fca6a8ded428cc24046f5b48b31d4043f2afbd9087d8946eaf4e10d71a5`.
Читатель входит в 3F0Eh; IRQ-вариант — в 3F17h, после штатного DI, с
подготовленным счётчиком попыток на стеке. Вход/возврат через 3D2Fh
подключает ROM TR-DOS. Диспетчер 3D13h используется при смене дорожки.
Адреса сверены с ROM и [дизассемблированием TR-DOS](https://github.com/programandala-net/tr-dos).
Для другой прошивки следует использовать `--disk-reader trdos`.
Измеритель проверяет хеш и явно передаёт ROM эмулятору; при нестандартном
размещении файл задаётся через `measure_fuse.py --trdos-rom /path/to/trdos.rom`.
Сам PLAYER не проверяет хеш ROM при запуске.

```text
4000–5AFF  экран банка 5
6000–6EFF  PLAYER и таблицы, 3840 байт
8000–9FFF  распакованный блок, до 8192 байт
A000–BCFF  сжатый ввод, до 7424 байт
BDBD–BDC3  быстрый ISR, 7 байт
BE00–BF00  таблица IM2, 257 байт со значением BDh
BF01–BFEF  область стека; начальный SP = BFF0h
C000–FFFF  банк кольца 0/1/3/4/6 либо экран 7
```

Сборщик отвергает блок с вводом больше 7424 байт; плеер проверяет границу
до копирования. Автоматическое дробление таких блоков пока не реализовано.
В проверенном ролике максимальный ввод 7017 байт. Прерывания разрешены
внутри прямого секторного чтения; при полном диспетчере/поиске дорожки
используется IM1. Поэтому **часы всё ещё пропускают часть дискового времени**.
Системный FRAMES не решает это: обработчик TR-DOS не обновляет его.

Сравнение 16-битных сроков использует знаковую разность; допустимое отставание
меньше 32768 полей. Переполнение проверено тестом. Подкачка до 64 секторов
защищает следующий блок даже при накопленном отставании, но создаёт паузы.

В v9 первый остаток дорожки, начиная с заголовка, остаётся линейным; после
перехода на следующую дорожку применяется перестановка. Поля заголовка и
байты блоков совпадают с v8, кроме номера версии. Поле числа секторов
содержит логический размер потока; физическое размещение дополнительно
включает пустые позиции. Обычный PLAYER v8 такой поток не читает.

## Проверенные промежуточные варианты

| Изменение относительно указанной базы | Средний интервал, мс | кадр/с |
|---|---:|---:|
| v8 + только быстрые команды | 193,965 | 5,156 |
| Предыдущий + прямое чтение, линейные секторы | 187,650 | 5,329 |
| Предыдущий + чередование секторов, cpu-fields | 184,083 | 5,432 |
| v8 + серия из четырёх секторов, cpu-fields | 278,000 | 3,597 |
| v8 + deadline со штатным ROM/FRAMES | 208,973 | 4,785 |

Серия из четырёх секторов замедлила чтение и увеличила паузы, поэтому не
выбрана для итоговой сборки. Попытка оставить IM2 внутри полного диспетчера
зависала; этот код удалён. Восстановление после ошибок диска в прямом
IRQ-читателе остаётся непроверенным; экспериментальная сборка предназначена
для сравнения в эмуляторе с указанной ROM.

## Воспроизведение

Из `toolkit/`, с NumPy, OpenCV, Pillow и компрессором ZX0 2.2 из документации v8:

```text
python build_fast_sparse_trd.py --source-build SOURCE --output build_speed_v9 --packing zx0 --zx0 /path/to/zx0 --drawing registers --disk-reader trdos503-irq --disk-layout interleaved --pacing deadline
python -m unittest test_fast_drawing test_playback_schedule test_disk_layout test_blocked_stream test_packed_stream
python benchmark_playback_speed.py --output playback_speed_cycles.json
python measure_fuse.py /path/to/fuse.exe build_speed_v9 --output build_speed_v9/fuse_timing.json
python validate_fast_sparse.py build_speed_v9 --source-build SOURCE --fuse-timing build_speed_v9/fuse_timing.json --output build_speed_v9/cpu_validation.json
```

Источник: `build_long_center_crop_feedback_melody_no_gray_25over3fps`.
SHA-256 исходного `VIDEO_full.C.bin`:
`5d42a94efb0343fb3415c12dcc616bb9403b02f8946d7e8fbfaf45e7030f26e6`.
Краткие измерения и хеши итоговых файлов:
[playback_speed_measurements.json](playback_speed_measurements.json).
Полные трассы находятся рядом с готовым TRD в `build_speed_v9/`.

Проверки: 18 тестов, включая все 96 строк, обе экранные страницы, разреженные
и плотные маски, точные такты, границы кольца/банка/дорожки, переполнение
часов, ограничение ввода и прерывания во время вывода. Полный инструкционный
прогон сверяет 1000 экранов и AY с исходником при повторении расписания Fuse.
