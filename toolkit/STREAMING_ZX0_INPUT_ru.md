# ZX0 с частично загруженным входом: проверенный прототип ядра

26 сентября 2026. База `d4f31df`, точные блоки TRD `074e1e7` с HL-reader.
**Это отдельный CPU-стенд, не новый плеер или выпуск.** Байты FAP3/ZX0,
все кадры и звук сохраняются. Интеграция с очередью, bootstrap, TR-DOS
и проверка реального времени воспроизведения ещё впереди.

## Зачем это нужно

[Предыдущий профиль](ZERO_MASK_HISTORY_ru.md) связал первые недогрузки AY
на дисках 2/3 с ожиданием целого сжатого блока: один `take` читал 20/22
сектора. Частичное потребление **распакованного** слота уже есть, но оно
начинается лишь после полной загрузки его **сжатого** входа.

[Новое ядро](streaming_local_zx0.py) может работать сразу с первой доступной
страницей входа и приостанавливается перед переходом в недогруженную.
Сектор загружается прямо на окончательное место в `C000..DFFF`; копирования
через промежуточное 256-байтовое окно нет. История/выход остаются в
`E000..FFFF`. Поток и последовательность его байтов прежние.

## Безопасность границы входа

Контракт вызывающего кода: первая страница, содержащая начало ZX0, уже
доступна; загруженные страницы образуют непрерывный префикс. Во время
приостановки можно добавить целые страницы и продвинуть `input_high`.
`all_loaded` устанавливается только после загрузки всего блока.

1. Метаданные ZX0 читаются через HL. `INC HL` заменён на `INC L` и
   условный вызов обработчика границы. При переносе обработчик увеличивает
   H и проверяет доступность следующей страницы до очередного чтения.
2. Literal-серии делятся на части, не пересекающие границу 256 байтов.
   После части проверяется та же граница. Длинная серия поэтому не может
   прочитать недоступную страницу, даже превысив квант выхода.
3. Match-серии читают уже построенную историю; её прежние ограничения
   сохраняются. Курсор входа не перепрыгивает страницы. По индукции каждый
   переход из загруженной страницы либо попадает в следующий доступный
   участок, либо приостанавливается. Это условие не зависит от статистики
   данного мультфильма.
4. При нехватке входа сохраняются регистры и частный стек ZX0, возвращается
   `input_needed`. Повторный вызов без новых данных снова приостанавливается.
   Чтение Elias, offset и EOF защищено тем же механизмом.

Есть отдельный флаг **`finished`**. Равенство выхода длине блока ещё не
означает EOF: последний битовый заголовок может потребовать следующую
страницу. При входной паузе `resume` продолжает декодер даже при уже
достигнутой цели выхода. Будущая очередь обязана публиковать готовый слот
по `finished`, после завершения обработки общего последнего сектора.

Это контракт корректного потока/producer, а не новый валидатор произвольных
повреждённых дискет. На стенде отдельная защита дополнительно запрещает
чтение после конца сжатых данных и ещё не произведённой истории.

## Измеренная стоимость CPU

Оба ядра исполняются на одинаковых блоках с одинаковыми номинальными
запросами выхода через 256 байтов; входные паузы нового ядра повторяют
текущий запрос. База — прежний inline-literal ZX0. ROM, диск, IRQ, ULA,
очередь и переключения банков исключены из этой таблицы.

| Том | База, T | Прототип, T | Добавка, T |
|---|---:|---:|---:|
| 1, 126 блоков | 63454091 | 74269540 | +10815449 |
| 2, 123 блока | 67060720 | 78144292 | +11083572 |
| 3, 129 блоков | 70571286 | 81941450 | +11370164 |
| **Всего** | **201086097** | **234355282** | **+33269185 (+16,54%)** |

Абсолютные стоимости отдельных путей по [таблице Zilog UM008011](https://www.zilog.com/docs/z80/um0080.pdf):

- Продвижение входа без перехода страницы: `INC HL` **6 T** →
  `INC L; CALL Z,...` **4+10=14 T**, добавка **8 T** на такое чтение.
- Literal, целиком внутри страницы, без паузы, выход ниже старшего байта
  цели: от начала копирования до следующей ZX0-инструкции
  **21N+26 → 21N+106 T**, добавка **80 T**. В новой версии это включает
  CALL 17 T, проверку/переход 53 T и RET 10 T сверх прежнего встроенного пути.
- Обёртка обычного `resume` добавляет **27 T**, `begin` — **40 T/блок**,
  фиксация `finished` — **30 T/блок**. Пересечения страниц и входные паузы
  имеют отдельные ветви; все они включены в итоговую таблицу.

[Отчёт](streaming_zx0_input_cpu.json) сохраняет машинные байты, метки,
размеры/хеши блоков, все кванты/паузы и гистограммы исполненных
инструкций обоих вариантов. [Аудитор](verify_streaming_zx0_input.py) проверяет
T каждой инструкции по отдельной таблице и сверяет суммы инструкций,
блоков и томов. Новое ядро **480 вместо 314 байтов**, включая **21 вместо
15 байтов состояния**. Максимум частного стека на реальных блоках —
16 байтов без IRQ; с инъекциями AY проверена граница выделенных 112 байтов.

## Что происходит с двумя проблемными запросами

Повторены точные границы исходных запросов, включая остаток старого блока
и общий сектор с новым. Ниже индексы кадров внутри диска начинаются с нуля.

| Запрос | Диск 2, кадр 157 | Диск 3, кадр 56 |
|---|---:|---:|
| Байтов из старого блока | 49 | 729 |
| Требуется выхода нового блока | 1005 | 1165 |
| Весь сжатый новый блок, B | 5224 | 5569 |
| Реально прочитано ядром из него, B | 762 | 894 |
| Загруженный префикс, B | 970 | 922 |
| Новых секторов до получения данных: база → прототип | **20 → 3** | **22 → 3** |
| CPU нового префикса, T | 80065 | 120773 |

Общий сектор старого блока здесь учитывается как уже доступный. Это
исполнение ядра для **того же запроса**, а не воспроизведение новой очереди:
её состояния и фазы вращения изменятся. Число 3 нельзя преобразовывать
в прогноз времени без TR-DOS/Fuse. Остальные сектора всё равно потребуются
позже. На первом диске первый проблемный запрос не пересекал блок и не
читал диск; данный опыт не доказывает устранение этой задержки.

На всех данных 377 из 378 блоков начали выдавать результат до загрузки
всего входа; один малый блок поместился в первую доступную страницу.
Проверены 7492 входные паузы. Все 3083375 распакованных байтов точны;
исходный поток с заголовками остался **1919945 B**.

## Охват, ограничения и следующий шаг

Пять тестов проверяют длинные literal/match, все 256 начальных смещений
для случая EOF, границы страниц и банка, начало с целью ноль и разорванным
Elias-заголовком, повторное ожидание, неполный/лишний вход, заново заполненные
регистры вызывающего кода. AY IRQ внедряется после каждой инструкции
выбранной последовательности, кроме окончательного возврата вызывающему;
все регистры, звук и стек сохраняются. Сначала этот тест требовал произвольные
2000 инъекций и упал при корректных 1808; порог заменён точной проверкой
числа всех исполненных инструкций за вычетом окончательных возвратов.

Тестовое размещение `7800..79DF` **не подходит для установки в текущий
плеер как есть**: пересекает его служебные области. Следующая работа:

1. Вернуть встроенный быстрый literal-путь с проверкой входа, чтобы
   сократить нынешнюю добавку 80 T на короткую серию. Сравнить абсолютный
   CPU со здешней базой и повторить проверки всех блоков.
2. Разнести горячую часть в bank 2 и редкие обработчики в свободные
   фиксированные области; сохранить AY helper, producer, стек и таблицы.
3. Связать `input_needed` с чтением одного сектора, разрешить старт после
   доступного заголовка/первого байта и завершать общий сектор до смены
   слота. Учесть паузу прямо внутри `begin` и отдельный `finished`.
4. Пересобрать bootstrap в прежнюю ёмкость, проверить самостоятельные
   старты/смену диска и полностью пройти три TRD в Fuse с реальными OUT,
   IRQ, AY, ROM и диском. До этого ускорение всего плеера не установлено.

## Воспроизведение

Python/NumPy, `PYTHONPATH=toolkit`, из `.worktree/streaming-zx0-input`:

```powershell
python -m unittest toolkit.test_streaming_zx0_input
python toolkit/benchmark_streaming_zx0_input.py --directory ../hl-mask-reader/.tmp/hl
python toolkit/verify_streaming_zx0_input.py --directory ../hl-mask-reader/.tmp/hl
python toolkit/verify_streaming_zx0_input.py
python toolkit/verify_streaming_zx0_input.py --execute
```

Последние две команды работают без временных TRD: первая проверяет архивы,
исходники, код, таблицу тактов и два префикса, вторая дополнительно заново
исполняет оба ядра на всех 378 блоках. Обе проверки пройдены; повтор CPU
из архива совпал по всем выходным байтам и абсолютным тактам. Входы хранятся в
[архиве](streaming_zx0_input_evidence), его хеши — в
[манифесте](streaming_zx0_input_evidence.json). Новый Fuse-прогон, публикации
кадров, непрерывная подача AY и физический привод здесь не проверялись.
