# Код плеера в банке 2

## Результат полного ролика

База — `a55744f`, предварительная подготовка пакетов и сжатого входа.
Новый параметр `--uncontended` переносит исполняемый код в фиксированный
банк 2. Проверены все 1000 экранов и AY; видеоданные побайтно прежние,
112 блоков ZX0, 2517 секторов полезного потока, одна TRD и четыре свободных
сектора. PLAYER по-прежнему занимает 4608 байт / 18 секторов.

| Показатель, Fuse 1.9.0 / Spectrum 128 + Beta128 | До | После |
|---|---:|---:|
| Средняя скорость, кадров/с | 8,255 | 8,238 |
| Средний интервал, мс | 121,141 | 121,390 |
| Максимальный интервал, мс | 218,224 | 178,310 |
| Интервалов длиннее 125 мс | 171 | 123 |
| Старт до первого кадра, мс | 3533,745 | 3518,804 |
| Секторных чтений, включая заголовок | 2518 | 2518 |
| ROM во время воспроизведения, с | 19,369 | 19,366 |

Длинных интервалов стало на 28,1% меньше, максимальная пауза уменьшилась
на 18,3%. Средняя скорость слегка снизилась: это улучшение равномерности
показа, а не достигнутые плавные 8 кадров/с. Расписание по-прежнему задаёт
шесть полей на кадр, номинально 25/3 кадра/с; потери IRQ в ROM и тяжёлые
кадры остаются предметом следующего этапа.

## Почему перенос помогает

Прежний код начинался с 6000h, в банке 5. На Spectrum 128 нечётные банки
RAM разделяют доступ с ULA: инструкции могут ждать видеоконтроллер.
Фиксированный банк 2 по адресу 8000h таких задержек не имеет.
Это соответствует [карте памяти и модели contention в исходнике Fuse](https://raw.githubusercontent.com/fuse-emulator/fuse/master/machines/spec128.c).

| Область | Прежнее размещение | Новое размещение |
|---|---|---|
| Код и таблицы | 6000–71FFh | 8010–91FFh |
| История ZX0 и команды кадров, 8192 байта | 8000–9FFFh | 6000–7FFFh |
| Сжатый вход, до 7424 байт | A000–BCFFh | A000–BCFFh |
| Стек подготовки, нижняя граница / вершина | 7D00 / 7D70h | 9D00 / 9D70h |
| Стек ZX0, нижняя граница / вершина | 7D80 / 7DF0h | 9D80 / 9DF0h |
| ISR / таблица IM2 / главный SP | BD00, BDBD / BE00–BF00 / BFF0h | прежние |
| Кольцо секторов | 5 банков, 320 секторов | прежнее |

Теперь задержки возможны при работе с историей и командами в банке 5,
но частые выборки инструкций, таблиц и переменных идут из банка 2.
Дополнительного копирования каждого кадра нет. Сборщик проверяет границу
кода перед стеками; старое поддержание мотора через scratch-буфер 7C00h
запрещено для этого размещения, используется проверенный cached SEEK.

BASIC продолжает загружать PLAYER в 6000h. Первые 16 байт переносят
4592 байта тела из 6010h в 8010h и передают управление. Смещение 16 байт
поглощено выравниванием таблиц, поэтому размер файла и начало VIDEO
на дискете сохранились. Первый заголовок читается в 6000h уже после переноса.

## Точные Z80 T-states

Источник — [таблица Zilog UM0080](https://www.zilog.com/docs/z80/um0080.pdf).
Для одинакового пути инструкция с изменённым адресом имеет прежнюю
номинальную стоимость. Contention, IRQ, HALT, ROM и диск сюда не входят.

| Путь | До, T | После, T | Разность, T |
|---|---:|---:|---:|
| Два stored-пакета по 1000 байт, подготовка в основном цикле | 95 963 | 95 963 | 0 |
| Те же пакеты, полная фоновая подготовка | 116 330 | 116 330 | 0 |
| Маска, 0 / 32 изменённых байта | 984 / 2904 | 984 / 2904 | 0 |
| Точки, 0 / 8 | 217 / 1119 | 217 / 1119 | 0 |
| Два span по 16 байт | 3367 | 3367 | 0 |
| RLE: повтор 32 / литералы 32 | 1840 / 3119 | 1840 / 3119 | 0 |
| Короткий ISR, включая ACK и ROM mapper | 61 | 61 | 0 |
| Однократный перенос при старте | 0 | 96 471 | +96 471 |

Перенос: DI 4 + три LD rr,nn по 10 + LDIR (21×N−5) + JP 10 =
21×N+39 T; N=4592. Последний байт загрузчика — выравнивание, он не исполняется.
В фоновом тесте 24 порции, максимум 10 172 T. Границы измерения:
подготовка от входа подпрограммы до RET; рисование от входа команды до
JP command_loop, без диспетчера. [Машинный отчёт](player_relocation_cycles.json).

На полном ролике расписание и число фоновых вызовов меняются:

| CPU подготовки на кадр | До, T | После, T | Разность, T |
|---|---:|---:|---:|
| Основной цикл, среднее | 152 340,327 | 133 445,002 | −18 895,325 |
| Основной цикл, максимум | 580 183 | 520 264 | −59 919 |
| Фоновая подготовка, среднее | 66 641,394 | 87 728,510 | +21 087,115 |
| Сумма среднего основного и фонового CPU | 218 981,722 | 221 173,512 | +2191,790 |
| Наибольшая фоновая порция | 22 009 | 22 021 | +12 |

Сумма номинального CPU выросла на 1,00% из-за другого распределения работы.
Падение среднего основного CPU нельзя выдавать за такое же сокращение
полной стоимости кадра. Реальный выигрыш от памяти подтверждает только
полный прогон Fuse с contention и диском; ROM измерен отдельно в таблице выше.

## Проверки и отклонённые варианты

43 теста прошли. Новые проверки выполняют сам перенос, проверяют его
такты, работу длинных сжатых блоков с IRQ, stored-кадры, переходы секторов
и обоих экранов, конфликтующие размещения памяти. Отдельный CPU-прогон
сверил 1000 экранов и AY с исходником, воспроизводя часы из Fuse.
Fuse завершил ролик без fatal и недогрузки. Пиксели внутри Fuse отдельно
не сравниваются; физический дисковод не измерен.

Несколько банков распакованных блоков также проверены. Исправленный
трёхбуферный вариант сохранял все кадры, но давал максимум 259,633 мс;
после переноса кода — 243,931 мс. Копирование команд и уменьшение кольца
съели выигрыш. Отложенное чтение только в свободном временном окне привело
к недогрузке; дополнительная порция в последнем поле у прежней схемы
увеличила число длинных интервалов. Эти варианты в рабочий профиль не включены.

Следующий шаг: разложить оставшиеся тяжёлые интервалы на рисование,
подготовку блока и обязательную квоту чтений. Новое расписание должно
позволять вовремя показывать готовый кадр и переносить долг чтения,
сохраняя гарантированный запас секторов. Модель должна учитывать частично
занятый сектор; пропуск квоты без такого учёта уже показал недогрузку.
