# Полупиксельное предсказание четырёх уровней

18 сентября 2026. База `8dd09de`, полный принятый мультфильм: 4971 кадр,
256×192, логическая сетка 128×96, видео 25/3 fps. Исходные состояния:
`9cc006a31408e2c3c3f96f96901b003756c2a480497e12d6b124baedafaeb35d`.
Это отдельный опыт **без потерь** относительно принятого Spectrum-видео.
Он не включает ограниченные изменения пикселей лучшего кандидата `8dd09de`.

## Метод

Наши четыре значения обозначают заполнение INK в логическом пикселе 2×2:
0, 1, 2 или 4 из четырёх точек. Это не равномерная шкала яркости и не четыре
глобальных цвета: INK/PAPER задаются атрибутом соответствующей ячейки 8×8.

Помимо 81 целочисленного смещения ±4 логических пикселя, добавлены 120
смещений с половинной координатой в пределах ±3. Нулевая плитка — отдельный
предиктор. Плитки 8×8 логических пикселей; предыдущий кадр — источник.
Для половинного смещения смешиваются покрытия `[0,1,2,4]` и выбирается
ближайшее доступное. Сначала горизонталь, затем вертикаль, с округлением
на каждом шаге. Проверены оба направления округления при равенстве.
Вне экрана исходные точки равны нулю до смешивания.

Все поправки сохраняются точно; никакого сглаживания выходных кадров нет.
Атрибуты предсказываются из той же позиции предыдущего кадра, без движения.
Порядок полей — плитки 8×8, группы по 8 кадров, формат `HMR1` описан
в [кодере](probe_halfpel_motion.py). Критерий выбора движения прежний:
8 за ненулевой байт, плюс число изменённых битов, плюс 8 за ненулевой
индекс предиктора. Оптимальность этого критерия для ZX0 не доказана.

## Полный фильм

| Вариант | Сырой поток, байт | Ненулевые поправки рисунка | DEFLATE 8192 | Оптимальный ZX0 8192 |
|---|---:|---:|---:|---:|
| Целочисленный контроль | 5219634 | 1841463 | 2547449 | 2656092 |
| Половинный, округление вниз | 5157952 | 1779541 | 2541707 | не измерен |
| Половинный, округление вверх | 5139113 | 1760702 | 2529164 | 2628420 |

Здесь размеры сжатия включают 4-байтный заголовок каждого блока.
ZX0 экономит **27672 байта, 1,042%** относительно контроля того же формата.
Это больше лучшего кандидата с ограниченными изменениями пикселей
2509819 байт; сравнение этих двух чисел включает разницу в качестве.
С ранее измеренным AY 77696 байт половинный вариант даёт 2706116 байт,
на 768452 больше щедрого бюджета трёх TRD 1937664 до служебных расходов.

В верхнем варианте половинное смещение выбрано для 72109 из 954432 плиток:
в среднем 14,506, максимум 105 плиток на кадр. Из них 26978 горизонтальных,
24489 вертикальных, 20642 по обеим осям. Эти частоты не равны числу
операций смешивания байтов.

## Цена Z80

[Скрипт](benchmark_two_bit_lookup.py) содержит машинный код операции над
четырьмя упакованными двухбитными пикселями через таблицу 256 байт.
Входы уже выровнены в B/C, H указывает на страницу таблицы; результат A,
разрушаются D/L/флаги, B/C/H сохраняются. Код занимает 35 байт.

| Операция от входа до RET включительно | T-states |
|---|---:|
| Взять готовый исходный байт: `LD A,B; RET` | 14 |
| Применить таблицу смешивания | 148 |
| Разница для этого примитива | **+134** |

Это сравнение примитивов, **не декодеров кадров**. Не включены CALL,
загрузка/выравнивание входов, запись результата, циклы, paging, ZX0,
IRQ, ULA, ROM и физический диск. Для двух осей потребуется несколько
смешиваний. Таблица команд и сумма сохранены в JSON; использованы
[официальные времена Zilog, UM008011-0816](https://www.zilog.com/docs/z80/um0080.pdf),
стр. 71, 74, 158, 160, 209, 285. Интерпретатор подтвердил результат,
постоянное время и контракт регистров на всех 65536 парах входов для
контрольной операции и каждой из двух таблиц: 196608 исполнений.

Маски/векторы группы занимают 5376 байт, две компактные истории — 7680.
Для таблицы смешивания нужно ещё 256 байт. Это только части карты RAM:
размещение кода, экранов, ZX0, AY, IRQ, стека, TR-DOS и дискового кольца
вместе для нового формата не проверено. PLAYER/TRD не менялись, изменение
встроенного горячего пути **0 T**. Новых полных Z80/Fuse/дисковых замеров нет.

## Проверка и решение

- Все три потока независимо восстановлены в исходные 4971 кадр побайтно.
- Все 638 и 628 блоков ZX0 контроля и верхнего варианта распакованы
  независимым декодером; отчёты завершены.
- 5 тестов: неравномерная шкала и округление, обе стороны смещения,
  границы экрана/байта, вручную составленный поток с атрибутами,
  совпадение целочисленного поиска с прежним, полные синтетические
  восстановления и усечённый поток.

**Решение:** сохранить опыт, не переносить половинное движение в PLAYER
на этом этапе. Выигрыш около 1% не закрывает дефицит объёма, а CPU
усложняется. Полного сравнения скорости ещё нет, поэтому это приоритет
дальнейшей работы, а не доказательство непригодности метода. Следующий
опыт — более подходящий алфавит точных поправок для четырёх уровней.

## Воспроизведение

`CHECKPOINT` — принятый `source/conversion.npz`, `ZX0` — оптимальный ZX0 v2.

```text
python toolkit/probe_halfpel_motion.py --checkpoint CHECKPOINT --cache .tmp/halfpel --output toolkit/halfpel_measurements.json
python toolkit/probe_zx0_storage.py --raw .tmp/halfpel/integer_g8_9cc006a3.raw --block-bytes 8192 --zx0 ZX0 --cache .tmp/halfpel_zx0 --output toolkit/halfpel_integer_zx0_measurements.json --jobs 2
python toolkit/probe_zx0_storage.py --raw .tmp/halfpel/half_upper_g8_9cc006a3.raw --block-bytes 8192 --zx0 ZX0 --cache .tmp/halfpel_zx0 --output toolkit/halfpel_upper_zx0_measurements.json --jobs 2
python toolkit/benchmark_two_bit_lookup.py --output toolkit/two_bit_lookup_measurements.json --motion-report toolkit/halfpel_measurements.json --motion-cache .tmp/halfpel
python -m unittest discover -s toolkit -p test_halfpel_motion.py -v
```

Данные: [поиск и DEFLATE](halfpel_measurements.json),
[ZX0 контроля](halfpel_integer_zx0_measurements.json),
[ZX0 половинного движения](halfpel_upper_zx0_measurements.json),
[команды Z80 и все проверки](two_bit_lookup_measurements.json).
