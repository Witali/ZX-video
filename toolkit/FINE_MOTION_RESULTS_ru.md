# Точная компенсация движения с шагом в один пиксель

Дата: 18 сентября 2026. База опытов `a13c3fe`; контроль масок сохранён
в `2e4b23a`. Выпуск дискет остаётся `69754f3`.
**Все кадры сохранены точно; новый формат пока не является проигрываемым TRD.**

## Метод

Ранее поиск движения делался с шагом 4 логических пикселя. Здесь ПК ищет
смещения с шагом **1 логический пиксель**, то есть 2 физических, в пределах
±4 по обеим осям. Всего 81 смещение, включая нулевое; ещё один индекс
означает предсказание нулевыми байтами для появления пустых областей.
Выход за экран тоже заполняется нулём. Блоки: 4×4, 8×8 и 16×16 логических
пикселей. Все 4971 кадр остаются 128×96 / 256×192, 25/3 кадра/с.

Выбор предиктора выполняется на ПК. Его стоимость:
`8 × ненулевые байты XOR + ненулевые биты XOR + 8 за ненулевой индекс`.
Это эвристика для отбора, не точный размер ZX0 и не оценка CPU. При равной
стоимости выбирается первый предиктор — прежде всего нулевое смещение.
Атрибуты предсказываются из того же места предыдущего кадра, без сдвига.
Каждая ошибка предсказания передаётся: квантования или удержания здесь нет.

В `FMR1` группа из 16 кадров содержит индексы смещений, затем маски
ненулевых байтов поправок, затем сами поправки. История n−1 продолжается
между группами. Декодер читает упакованные исходные пиксели по координатам
и независимо восстанавливает весь поток; функции поиска и раскладки плиток
при восстановлении не используются.

## Измерения полного фильма

Предварительный отбор DEFLATE, блок 8192. Включены индексы, таблица
смещений, маски, поправки и заголовки. Звук и проигрыватель не включены.

| Блок логических пикселей | Сырой поток | DEFLATE | Векторы + маски группы в RAM |
|---|---:|---:|---:|
| 4×4 | 7594144 | 2620852 | 19968 |
| 8×8 | 5219011 | **2542062** | 10752 |
| 16×16 | 4770541 | 2581022 | 8448 |
| Контроль n−1 без движения, тот же размер группы | 4973342 | 2803293 | 7680 |

Меньший сырой поток не обязательно лучше сжимается. Для настоящего ZX0
выбран блок **8×8**:

| Формат | Оптимальный ZX0 v2, блоки 8192, с заголовками |
|---|---:|
| Точный контроль n−1, группы 16, без движения | 2920696 |
| Точное движение 8×8, шаг 1 | **2660953** |

Выигрыш относительно контроля: **259743 байта (8,89%)**.
Относительно прежнего лучшего точного замера 2894676 байт —
**233723 байта (8,07%)**. Прежний замер разделял маски всего фильма;
здесь данные сгруппированы по 16 кадров. Это сравнение хранения, не скорости.

Бюджет трёх TRD до дополнительных расходов: 1937664 байта. Одно видео
превышает его на **723289 байт**. С ранее измеренными 77696 байтами AY
получается **2738649**, превышение **800985 байт**. Нужно убрать ещё
около 29,25% этого объёма плюс учесть загрузчик, декодер, начальные кадры
на границах томов и физическое размещение секторов. Цель пока не достигнута.

## Остаток и память

Для варианта 8×8 передано 1841463 ненулевых байта рисунка и 36242 байта
атрибутов; движение выбрано для 180664 из 954432 блоков, нулевой предиктор —
для 8833. В статистике остатка 1877705 значений; 15 самых частых покрывают
57,32%. Простая схема «частое значение — 4 бита, прочее — escape + 8 бит»
экономила бы приблизительно 137445,5 **сырых** байта до выравнивания,
таблиц и взаимодействия с ZX0. Это расчёт по гистограмме, не замер кодека.
Эмпирическая энтропия значений — 6,147655 бит/байт; она не является
нижней границей размера фильма и не учитывает контекст/повторы.

10752 байта в таблице RAM — только векторы и маски 16 кадров.
Прямая реализация с двумя компактными историями потребует ещё 2×3840,
всего **18432 байта** до ZX0, кода, стеков и прочих данных. ZX0-история,
оба аппаратных экрана, AY/IRQ и TR-DOS также остаются в бюджете 128 КБ.
Поэтому нельзя считать, что весь новый декодер автоматически помещается
в один освобождённый банк 16 КБ. Группа 8 уменьшила бы векторы/маски до
5376 байт; её реальный ZX0 и доставка с меньшим кольцом пока не измерены.

PLAYER не изменён, **горячий путь до/после тот же, разница 0 T**.
Для нового формата Z80 T-states ещё не получены. Нужно учесть копирование
из n−1, сдвиги упакованных пикселей, поправки, развёртку, paging и чтение
секторов; нельзя переносить измеренные 8⅓ fps прежнего выпуска на прототип.

## Проверки и решение

- Все три потока независимо восстановили все 4971 компактный экран
  побайтно: SHA-256 `9cc006a31408e2c3c3f96f96901b003756c2a480497e12d6b124baedafaeb35d`.
  Изображение и атрибуты точные; звук не изменяется.
- Все **638 блоков оптимального ZX0** независимо распакованы и сравнены.
- Четыре теста прошли: сдвиг через границу упакованного байта, независимо
  составленный поток с нулевым предиктором, края экрана/все размеры плиток,
  усечённые данные и недопустимый индекс.
- Восстановление потока на ПК проверено; нового Z80/Fuse-прогона и
  проверки дисковой доставки нет. TRD не пересобирались.

Сохранить этот результат как более сильную точную базу. В выпуск пока
не включать: трёх дискет не достигает, скорость и распределение памяти
не проверены. Следующий опыт: соединить компенсацию движения с ограниченной
ошибкой относительно каждого исходного кадра, не допускающей долгого
удержания; сравнить кодирование остатка и более короткие группы масок.
Любое ухудшение проверять по кадрам и в движении до изменения выпуска.

## Воспроизведение

`CHECKPOINT` — полный принятый `source/conversion.npz`; `ZX0` — ZX0 v2.

```text
python toolkit/probe_fine_motion.py --checkpoint CHECKPOINT --cache .tmp/fine_motion --output toolkit/fine_motion_measurements.json --tiles 4 8 16
python toolkit/probe_zx0_storage.py --raw .tmp/fine_motion/fine_motion_t8_r4_p8_g16.raw --block-bytes 8192 --zx0 ZX0 --cache .tmp/fine_motion_zx0 --output toolkit/fine_motion_zx0_measurements.json
python toolkit/analyze_fine_motion_residuals.py --raw .tmp/fine_motion/fine_motion_t8_r4_p8_g16.raw --output toolkit/fine_motion_residual_statistics.json
python -m unittest discover -s toolkit -p test_fine_motion.py -v
```
