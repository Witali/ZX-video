# Выбор быстрых фрагментов с ограничением объёма

25 сентября 2026, база `94c2e6f`. **Эксперимент на третьем томе,
не новый выпуск.** Разрешение, изображения и AY-данные не менялись.

## Причина и область опыта

В проигрывателе уже есть подготовка одного следующего compact-кадра,
следующего пакета и очередь ZX0. Поэтому в этом опыте уменьшается сама
работа при восстановлении: некоторые плитки с движением или Хаффманом
заменяются существующими готовыми фрагментами 85..88. Нового Z80-формата
или машинного кода нет. Выбор выполняется только при конвертации на PC.

Взяты текущие состояния без титров, все **4221 кадр**, и таблицы Хаффмана
тома 3. Меняются только кадры **2921..4220**, то есть все 1300 кадров
самой медленной дискеты. Начальный checkpoint, кодовые таблицы, native
карты и аудиозаписи сохраняются. Это не результат для всех трёх томов.

## Отбор

Проверены допуски **0, 16 и 64 бита** к локальному росту на плитку:

`8 * байты_фрагмента − биты_Хаффмана − 8 * ненулевые_байты_маски`.

Дополнительно требуется оценка экономии не менее 400 T. В неё входят
цены текущих motion/intra/fragment bodies по таблицам инструкций и
консервативные 150 T на удаляемый символ Хаффмана. Применение временных
поправок и часть управления намеренно не входят. Это эвристика отбора,
не точная цена нового кадра: выравнивание оставшихся кодов и метаданные
тоже меняют работу. Существующая карта motion-cache сохраняется как
безопасное избыточное покрытие; при полном отсутствии движения кэш отключается.

Готовые фрагменты содержат конечные байты изображения, а не приближение.
Независимый скалярный decoder восстановил все 4221 кадр и прежние AY
для каждого кандидата. Контрольная пересборка без выбора побайтово
совпала с исходным FAP3. Значение callback по умолчанию — `None`.

## Настоящий optimal ZX0 и раскладка дискеты

Блоки до 8192 распакованных байт, с теми же абсолютными границами
разбиения Builder и принудительным native map первых двух cold-кадров.
Каждый блок проверен независимым распаковщиком. В поток входят 4-байтовые
заголовки блоков. Затем собран настоящий старый независимый bootstrap
с исходными опциями, включая deferred=248, keepalive=64 и frame service.

| Допуск, бит | Заменённых плиток | Кадров | Поток ZX0, байт | К базе | Всего секторов TRD | Свободно из 2544 |
|---|---:|---:|---:|---:|---:|---:|
| База | 0 | 0 | 638742 | 0 | 2543 | 1 |
| 0 | 50 | 36 | 638789 | +47 | 2543 | 1 |
| 16 | 1413 | 429 | 639650 | +908 | 2545 | −1 |
| 64 | 4843 | 917 | 650358 | +11616 | 2589 | −45 |

У варианта 0 данные до ZX0 уменьшились на 32 байта, но после ZX0 выросли
на 47 байт. У 16/64 исходные данные выросли на 1395/19445 байт.
Отсюда практический вывод: локальная цена Хаффмана/масок недостаточна
для гарантии размера после внешнего сжатия. Изменяются также совпадения
ZX0 и границы блоков.

Логических секторов потока 2496/2496/2499/2541; padding чередования
соответственно 1/1/0/2. Поэтому вариант 16 добавляет три логических
сектора, но только два физических. Суммарный номинальный запас трёх
прежних образов этим исчерпывается; переразбиение с новыми checkpoint
не измерено. При прежних границах третья дискета переполнена на сектор.
Вариант 64 превышает её ёмкость уже на **11520 байт**.

Это ёмкость с прежним bootstrap, до отладочной установки slot queue и
compiled masks. Новые выпускные образы не создавались. Загружаемость
over-capacity вариантов не заявляется: Builder возвращает для них
`image=None`, сохраняя полную раскладку и параметры независимого загрузчика.

## Реально исполненные такты и экраны

Для варианта 64 на Z80-модели исполнены **все 1300 кадров третьего тома**:
метаданные, реконструкция, кэш, native output, переключения банков,
контроллер атрибутов. На каждом кадре проверены каждый compact-байт
и оба полных native-экрана. Медленнее базового не стал ни один кадр.

| Метрика | База | Кандидат | Разница |
|---|---:|---:|---:|
| CPU стадии всех кадров, T | 318721798 | 309822828 | **−8898970** |
| Относительная цена стадии | 100% | 97,21% | **−2,79%** |

База — сохранённое полное исполнение тома из
[`uncontended_frame_cpu.json`](uncontended_frame_cpu.json), где перенос
операндов имел проверенную дельту 0 T. Старый вариант заново целиком
не исполнялся. Обе стороны используют обычную распаковку метаданных,
carry Huffman и register fragments; compiled masks сюда не добавлены.
Такты каждой исполняемой инструкции проверяются по listing текущего
декодера. Новых инструкций в player нет: разница машинного кода **0 байт**.

**Не включены:** ZX0, пакетный reader, очередь, AY/видео IRQ, ULA, ROM,
физический диск и ожидания сроков. Эвристика отбора обещала лишь
5698402 T; настоящий полный stage-прогон дал другую величину выше.
Это не ускорение всего проигрывателя на 2,79% и не проверка 8⅓ fps.
Для вариантов 0/16 полного CPU-прогона не было. Fuse здесь не запускался:
вариант с измеренным выигрышем не проходит ёмкость текущего тома.

## Попытки, проверки и решение

- Первый вызов сборки остановлен несовпадением контрольного baseline:
  скрипт не передал deferred/keepalive/frame-service опции исходной сборки.
  После их явного переноса контроль совпал по объёму потока, стартовому
  сектору видео и общей занятости. Числа выше относятся к исправленному
  полному повтору; измеренные ZX0 и CPU от этого не менялись.
- Тест callback проверяет отключённый путь, выбор внутри заданного диапазона,
  сохранность всех изображений/AY и число замен. Он прошёл.
- Отчёты сопоставлены по хешам, покадровым тактам, полному покрытию третьего
  тома и физической раскладке; специальный проверяющий скрипт сохранён.

**Решение:** не включать широкую политику в основной converter. Она даёт
небольшой выигрыш CPU ценой недопустимого текущего размера; общий темп с
диском не проверен. Вариант 0 укладывается, но слишком мал для решения
нынешних опозданий; сам по себе выпуском не является. Полезное следующее
направление — отбор замен по фактической цене блоков ZX0 вместе с ценой
исполнения и работа с границами блоков. Это не доказательство невозможности
других политик/кодеков. Цель трёх дискет с точными сроками остаётся открытой.
