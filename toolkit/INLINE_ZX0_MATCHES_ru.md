# ZX0: копирование совпадений без повторного CALL/RET

24 сентября 2026, база `80ab9d9`. **Распаковка быстрее, трёхдисковый выпуск
с точными сроками не получен.** Вариант доступен через `--inline-matches`
в сборщике TRD и универсальном конвертере; по умолчанию выключен.

## Причина и изменение

В восьми кадрах с начала 2919 прежний CPU-профиль отводил ZX0 1 733 667 T
из 4 893 221 T (35,4%), восстановлению компактного кадра — 31,3%,
native-выводу — 22,3%. Битовые расчёты видеокодека здесь не единственная
существенная работа. Проверен небольшой независимый резерв распаковщика.

Turbo ZX0 вызывал ограниченный копировщик через `CALL slice_copy` для каждого
совпадения. Новый вариант вставляет эту проверку и копирование непосредственно
в тело декодера совпадений. Литералы сохраняют прежнюю процедуру с обработкой
границы 256-байтового входного окна. Декодер по-прежнему может остановиться
между копиями, сохранить свой стек и продолжить после произвольной работы
вызывающего кода. Байты ZX0, порядок токенов и момент остановки по позиции
выхода прежние; IRQ продолжает работать.

Теперь два набора изменяемых операндов сравнения цели. `slice_sync_target`
обновляет оба перед стартом/продолжением. IRQ не вызывает распаковщик,
поэтому не наблюдает промежуточные значения. Это изменение исполнения
**того же ZX0**, не новый формат видеоданных или новый алгоритм с потерями.

## Абсолютные такты

Счётчик исполнения основан на [таблице Z80](https://www.zilog.com/docs/z80/um0080.pdf).
Скрипт [summarize_inline_matches.py](summarize_inline_matches.py) исполняет
каждую ветвь, проверяет результат, регистры, carry и стек. В стоимости
старого пути учитываются внешний CALL (17 T) и RET (10 T); у нового
переход к следующей инструкции декодера происходит непосредственно.

| Ветвь | Длина | Прежде | После | Разница |
|---|---:|---:|---:|---:|
| Выход ниже старшего байта цели | 3 | 116 T | 89 T | −27 T |
| Тот же старший байт, младший ниже цели | 3 | 141 T | 114 T | −27 T |
| Последний байт FFFF→0000 | 1 | 106 T | 79 T | −27 T |
| Синхронизация обычной цели | — | 100 T | 139 T | +39 T |
| Синхронизация полной цели 0000 | — | 108 T | 147 T | +39 T |

Для первого пути: старая обвязка с CALL — 58 T, новая — 31 T;
сама `LDIR(n)` в обеих версиях стоит `21*n−5`. Для второго — 83/56 T.
Три дополнительные `LD (nn),A` стоят `3*13 = 39 T` на синхронизацию.

На одинаковых запросах точная формула изменения всего декодера:

`ΔT = 39 × число синхронизаций цели − 27 × число совпадений`.

Она проверена на коротких/длинных совпадениях, stored-блоках, границах
8192 байта, переходах входного окна/кольца и полном эталонном потоке.
Stored-блок без совпадений получает только накладные расходы; ускорение
не универсально для любого возможного ввода.

## Все 379 блоков фильма

Вход: прежний FAP3 всех 4221 кадров, SHA-256
`1aff3a304635025c25cc8b20d066b6044f2767b02c99d2490c9f9ae1613ac2ab`.
Расшифровывается весь файл, включая заголовок; эти глобальные границы
отличаются от обрезанных граничных блоков отдельных TRD.

| Показатель | Прежде | После |
|---|---:|---:|
| Все инструкции распаковки | 278 252 736 T | **266 673 453 T** |
| Максимальный фиксированный запрос | 42 440 T | 40 076 T |
| Машинный код со состоянием отдельного стенда | 620 байт | 651 байт |
| Максимум частного стека без IRQ | 18 байт | 18 байт |
| Переключения банков | 15 584 | 15 584 |

Экономия **11 579 283 T / 4,1614%**. Все 379 блоков побайтно восстановлены;
замедлившихся блоков нет. Исполнено **446 343 совпадения** и **12 102
синхронизации**: `39*12102 − 27*446343 = −11579283` точно совпало с
гистограммой. Запросы заданы на позициях 256/512/…/EOF; первый payload
расположен в кольце FFF0, последующие учитывают длину payload и заголовка.

Включены input refill, RAM-копирование, paging и продолжения. Исключены
потребитель кадров, IRQ, ULA, TR-DOS и физическая дискета. 4,16% нельзя
считать процентом ускорения всего проигрывателя. Максимум запроса выше
относится к измеренному фиксированному разбиению; новая универсальная
граница времени lookahead этим опытом не доказывается.

## Кадровый CPU-профиль

Восемь одинаковых диапазонов по 32 кадра, с началами
62/408/1269/2159/2334/2919/3195/3838. В каждом варианте исполняются
настоящие пакеты, ZX0, реконструкция, вывод, IM2, AY и прогресс;
источник дисковых байтов идеален, ULA/ROM/диск не моделируются.

**93 339 260 → 92 527 268 T**, −811 992 T (около 0,87%) переднего плана
за 256 кадров, включая предварительную подготовку. IRQ и ожидание отдельно.
Все 3840 компактных байтов и оба экрана по 6912 байт проверяются после
вывода/публикации, все AY-записи точны: обе пары суммарно **512 кадров /
3072 AY-записи**. В самых тяжёлых диапазонах остаются 27 и 12 поздних
публикаций; остальные короткие диапазоны укладываются в идеальные сроки.
Это локальные старты с подготовкой первых кадров, не расписание всего фильма.

## Полный Fuse и размер дисков

Два полных набора по 4221 кадру и 25 326 AY-записей. Границы
`[1269,2334,3195,4221]`, прежние разрешение, пиксели и звук. Первый набор —
обычное немедленное чтение; второй — ранее измеренный лимит отложенного
чтения 248, обслуживание после кадра, keepalive 64 поля. Оба используют
прямое TR-DOS 5.03 чтение, cached seek и interleave. Каждый новый том
пройден до EOF; старые полные измерения взяты из сохранённых отчётов
с тем же входом, границами, настройками и проверенными прежними генераторами.

Время проигрывателя от старта до завершения, суммарно по четырём дискам,
без bootstrap/смены: **565,8081 → 563,0333 с** и **560,6127 → 557,4277 с**.
Средняя скорость выросла, но основной критерий — точные сроки — у
отложенного варианта ухудшился: **3873 → 4043** нарушений. У немедленного
чтения **4096 → 4087**. Меньшая работа CPU меняет моменты обращения к диску;
это наблюдаемое сочетание скорости и расписания, не доказательство отдельной
причины каждого опоздания.

По новым вариантам максимальные отклонения по четырём дискам:
**8,0366 / 10,0957 / 20,9911 / 17,2127 с** и
**4,9979 / 8,8962 / 20,9112 / 16,0132 с**.
Восстановленных серий опозданий **5/6/0/1** и **4/2/6/3**; на каждом
диске остаётся одна невосстановленная. Резервный допуск одного поля также
не выполнен. Проверяются реальные OUT и счётчики с допуском фазы 64 T.
Полные номера пропущенных сроков восстанавливаются из сохранённых
`publications`/`actual_phase_tstates`; поздние серии сохранены явно.

Пропуски физических полей AY уменьшились **2939 → 2801** и **2686 → 2527**,
но требуемые 50 Гц всё ещё не выполняются. Последовательности всех записей
точны. Проверены 80 экранных байтов на каждый кадр — это выборка изображения,
а не полное сравнение экрана в Fuse. В двух наборах проверены **13 032
runtime-сектора** целиком, без повторных чтений. Интервалы обслуживания
нового чтения суммарно **200 972 793 T** и **200 891 424 T**, включая ROM,
механику эмулятора, contention и IRQ. Они не прибавляются к CPU-профилю;
чистая механическая задержка отдельно не измерена. Физический привод
не проверялся.

Поток каждого набора прежний: **1 929 884 байта**. Секторы с bootstrap
и физической раскладкой тоже прежние: **1930/1964/1961/1952** и
**1930/1964/1961/1953**. Число дискет остаётся четырьмя; выигрыш сжатия 0.
Корневые TRD не заменены; временные экспериментальные образы не добавлены
в Git. Существующие правила LFS сохранены.

## Память и совместимость

Новых буферов и переменных состояния нет; добавлено **31 байт кода** в
прежнем свободном промежутке. В реальном плеере с atomic paging и disk hook
декодер занимает **625 → 656 байт**, `7C00..7E8F`; загрузчик начинается
точно с `7E90`. Добавлена явная проверка непересечения. [Раскладка 128 КиБ](PIPELINED_FRAME_ru.md#раскладка-128-киб)
прежняя: кольцо 64 КиБ в банках 0/1/3/4, Huffman в 6, экраны/история/код
в 5/7, фиксированные код/окна/AY/стеки в 2. TR-DOS workspace не занят.
IRQ проверен после каждой инструкции тестового декодирования; сохранность
регистров/банка, границы частного стека и работа AY подтверждены тестом.

Без опции все старые генераторы побайтно сохраняются. Десять прежних
тестов banked/token-boundary декодеров прошли; итоговый набор интеграции
и новых проверок — **32 теста**, все прошли. Эти числа не суммируют повторные
запуски одной проверки.

Универсальный конвертер проверен на шести новых сборках синтетических
входов: один кадр, портрет, цветное видео с mono-звуком и тремя томами,
неквадратные исходные пиксели, звук длиннее видео, 48 шумовых кадров.
Все **68 кадров / 408 AY-записей** полностью сверены CPU-профилем;
все восемь TRD завершили Fuse, шумовой тест выполнил 78 runtime-чтений.
Первые пять входов прошли сроки, шумовой не прошёл — это сохранено как
отрицательная проверка ограничений. FAP3 всех шести входов побайтно совпал
с прежним [`generic_converter_checks.json`](generic_converter_checks.json).
[Новый отчёт](inline_matches_generic.json).

**Решение:** сохранить как измеренную оптимизацию CPU и явную опцию
конвертера/сборщика. Автоматически не включать: регрессия номинальных сроков
в сочетании с отложенным чтением важнее небольшого роста средней fps.
Следующее изменение должно учитывать моменты получения секторов и тяжёлые
кадры, а не только суммарные такты распаковщика. Цель — максимум три TRD,
нулевые опоздания, прежние разрешение и AY — остаётся невыполненной.

## Воспроизведение

Из корня; `$raw`, `$states`, `$zx0`, `$cache`, `$fuse`, `$rom`, `$ffmpeg`,
`$ffprobe` — пути к входам и инструментам. Входы и SHA приведены выше.

```powershell
$env:PYTHONPATH = 'toolkit'
python toolkit/benchmark_banked_zx0.py --raw $raw --storage-report toolkit/lean_frame_zx0.json --cache $cache --baseline-cpu toolkit/token_boundary_fast_banked_cpu.json --baseline-commit 80ab9d9 --fast-literal --fast-refill --token-boundaries --inline-matches --profile --output toolkit/inline_matches_banked_cpu.json
python toolkit/profile_inline_matches.py --raw $raw --states $states --zx0 $zx0 --read-cache $cache --cache .tmp/zx0 --report toolkit/inline_matches_frames_cpu.json
python toolkit/run_deferred_disk.py --raw $raw --states $states --zx0 $zx0 --read-cache $cache --fuse $fuse --limits 0,248 --keepalive-fields 64 --frame-service --inline-matches --output .tmp/disks --report toolkit/inline_matches_disk_summary.json
python toolkit/archive_deferred_disk.py --source .tmp/disks --summary toolkit/inline_matches_disk_summary.json --output toolkit/inline_matches_evidence
python toolkit/test_fap3_disk.py --volumes .tmp/disks/limit-248 --output toolkit/inline_matches_swaps.json
python toolkit/check_generic_converter.py --output .tmp/generic --ffmpeg $ffmpeg --ffprobe $ffprobe --zx0 $zx0 --fuse $fuse --trdos-rom $rom --inline-matches --report toolkit/inline_matches_generic.json
python toolkit/summarize_inline_matches.py --output toolkit/inline_matches_summary.json
python -m unittest test_inline_zx0.InlineZX0Tests test_stream_reader_z80 test_pipelined_frame test_fap3_disk test_generic_converter test_lean_checkpoints -v
python -m unittest test_token_boundary_zx0 test_banked_zx0 -v
```

Для произвольного видео добавьте `--inline-matches` к обычной команде
`convert_video.py`. Для диагностики других кадров `profile_inline_matches.py`
принимает `--ranges START:END,...`, конец исключительный.
